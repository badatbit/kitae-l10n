# 가변폭 — 조사와 계획

`風雨来記3` 한글화(`f:/dev-furaiki3/furaiki3-l10n`)에서 같은 문제를 이미 뚫었다.
**아키텍처는 완전히 다르지만 방법은 그대로 옮겨진다.** 그쪽 문서
`docs/engine/font-format.md` §5 와 `docs/localization-worklog.md` §2 가 원본이다.

## 우리 쪽에서 확인한 것 (2026-08-08)

전각 격자가 고정이라는 것을 **인게임으로 확정**했다. `HANYOU` 창 ３１２ 에 ASCII 를
넣어 보았다.

```
Hi, there! I'm testing th        ← ２５글자에서 잘림
iiii mmmm WWWW ....  0123        ← ２５글자에서 잘림
```

  * `iiii`·`mmmm`·`WWWW`·`....` 네 덩어리의 **길이가 같다.** 반각 글리프는 １２px 로
    좁게 그려지지만 자리는 전각 하나를 그대로 먹는다 → **펜 전진은 고정 피치**
  * 두 줄 다 정확히 **２５글자**에서 잘렸다 → 상한은 픽셀이 아니라 **글자 수**다
    (레코드 배열 `obj+0x84`~`0x213` = ２５×１６B, [MTG-TIMING.md](MTG-TIMING.md))

실험 스크립트는 `tools/legacy-src/_exp_propwidth.py.txt`(퇴역 보관) 에 남겨 두었다
(`--revert` 로 되돌린다).

## ★ 그래서 우리는 **미관만** 얻는다

`風雨来記3` 는 픽셀 폭으로 줄이 접혀서 가변폭이 곧 용량이었다. 우리는 다르다.
**한 줄 ２５글자 상한은 레코드 개수 제한이라 폭과 무관하다.** 공백을 좁혀도
２６번째 글자는 여전히 안 그려진다.

앞서 이 저장소에서 "공백을 좁히면 줄당 ２~３글자를 번다" 고 적었던 것은 **틀렸다.**

얻는 것은 하나뿐이지만 작지 않다 — **한글 어절 사이가 전각(２４px)이면 성기다.**
`風雨来記3` 는 셀 ２５ 에서 공백을 **６px** 로 줬다. 그 차이가 글꼴의 인상을 바꾼다.

## 그대로 옮겨지는 것

### 폭의 출처

IBM Plex Sans KR 의 실제 advance. 우리도 같은 글꼴을 쓴다. 우리 코드페이지
１,０４４자를 재 보니 **한글 음절은 전부 같은 폭**이었다(`@25px` 에서 ２２px) —
`風雨来記3` 쪽 표(셀 ２５ 에서 한글 １,３６４자가 전부 ２０)와 성질이 같다.

즉 **한글끼리는 한 픽셀도 안 줄어든다.** 실익은 공백·문장부호·라틴·숫자에 있다.

| | 셀 ２５ 기준 (`風雨来記3` 실측) |
|---|---|
| 한글 음절 | ２０ |
| 공백 | **６** |
| `.` `,` | ６ |
| 숫자 | １３ (tabular) |
| `m` | １９ · `M` `…` １８ · `%` ２１ |
| 전각 기호 `「」『』、。・` | ２５ (미해결 — 잉크는 ５~７px 인데 칸을 다 먹는다) |

### 구현 얼개

슬롯 번호로 바로 인덱싱하는 **１바이트 폭 표**를 새 PE 섹션에 두고, 렌더러의
전진 계산 자리에 훅을 걸어 표를 조회하게 한다. 밴드(구간 비교 체인)로도 되지만
`風雨来記3` 는 결국 표로 통일했다 — 밴드는 "슬롯 순서 = 폭 오름차순"을 요구해서
**글자를 하나 더할 때마다 배정이 전부 밀린다.** 우리는 코드페이지가 계속 자라므로
처음부터 표로 간다.

### ★ 글리프를 왼쪽 정렬로 다시 그려야 한다

지금 `hangul.render_glyph` 는 잉크를 셀 **가운데**에 놓는다.

```python
x = (24 - (box[2] - box[0])) // 2 - box[0]      # ← 가운데 정렬
```

전진폭을 좁히면 가운데 정렬된 잉크가 **자기 칸을 벗어난다**(`風雨来記3` §6 이
같은 함정을 적어 두었다). 펜 원점(좌측) 정렬로 바꾸고 폰트 전체를 다시 구워야
한다. 기준값: 그쪽 ２５px `.` `,` 는 잉크 x １..４ / 전진폭 ６ 이다.

### 되돌릴 수 있게 만든다

`風雨来記3` 는 훅마다 `on` 스위치를 두고 화면 단위로 켰다. 우리도
`emulator_fixes` 처럼 설정 한 줄로 끄고 켤 수 있어야 한다 — 대사창만 켜고
가이드북·메뉴는 순정으로 두는 것이 첫 목표다.

## 우리에게만 있는 벽

`風雨来記3` 는 x86 단일 exe 였다. 우리는 **SH4 · WinCE · DLL 여러 개**다.

```
TRFFONT.DLL   CTRFFont::DrawChar 0x10001240 — 폭을 돌려주지 않는다(에필로그 확인)
KITAE.DLL     대사창.  TRFFONT 를 임포트하지 않고 클래스 이름으로 찾아 가상 호출
TRFGUIDEMAP   가이드북
KITACMDMENU   커맨드 메뉴·선택지
```

전진을 계산하는 주체가 **모듈마다 따로**다. 나쁜 소식이자 좋은 소식이다 —
한 곳을 고쳐 전부 바꿀 수는 없지만, **대사창만 고쳐도 다른 화면이 안 깨진다.**

### ★ 규명 끝 — 글자 엔진은 `TRFSTRINGS.DLL` 이다 (2026-08-09)

내내 `KITAE.DLL` 을 뒤졌던 것이 헛수고였다. `TRFSTRINGS` 를 **폰트 데이터 덩어리로만**
보고 지나쳤는데, 이름 그대로 TRF **Str**ings — 글자 엔진 본체다(`.text` ４６KB).
[MTG-TIMING.md](MTG-TIMING.md) 가 인용한 주소가 전부 여기서 맞아떨어진다.

```
0x10007C30   mov #25,r3 · cmp/gt · mov #25,r2     한 줄 25글자 상한 (화면과 일치)
0x10007524   BuildTiming 프롤로그
0x100076CC   토크나이저 프롤로그
```

모든 DLL 이 `ImageBase 0x10000000` 이라 **주소 범위만으로는 모듈을 가릴 수 없다.**
클래스 이름(`ITRFStrTiming`)으로 갈라야 한다 — `TRFFONT`·`TRFKernel` 에는 없다.

### 글자 루프 `0x10003558`~`0x100035C8`

```
0x1000357a  mul.l  r11,r1        ; r1 = @(20,r15) 레코드 보폭 × r11(글자 인덱스)
0x10003582  add    r4,r8         ; r8 = 레코드 배열 + 인덱스*보폭  → 이번 글자의 레코드
0x100035a8  mov.l  @r9,r6        ; 폭을 그리기 호출에도 넘긴다
0x100035b4  mov.l  @r9,r4        ; ★ 폭 읽기 — 즉치가 아니라 객체 필드
0x100035b8  add    @(52,r10),r4  ; + 자간
0x100035be  sub    @(48,r10),r4  ; − 보정
0x100035c6  bt/s   0x10003558    ; 다음 글자
0x100035c8  add    r4,r12        ; ★ 펜 X 전진
```

  * `r13` 글꼴 객체(가상 호출) · `r11` 글자 인덱스 · `r12` **펜 X** · `r8` 이번 레코드
  * **`@r9` 는 모든 글자에 같은 값**이다 = 셀 고정 폭. `add #24` 같은 즉치를 아무리
    찾아도 안 나온 이유다

### 그래서 (가) 였다

앞서 갈랐던 두 갈래 중 **글자마다 폭을 더해 가며 미는 형태**다. 열 번호 × 고정폭이
아니다. `0x100035B4` 의 `mov.l @r9,r4` 를 **슬롯→폭 조회**로 바꾸면 된다 — 훅 하나다.
`風雨来記3` 의 `add esi,eax` 와 같은 자리이고, 우리는 `add r4,r12` 다.

게다가 `TRFSTRINGS.DLL` 은 **폰트 글리프를 넣느라 매 빌드 이미 패치하는 파일**이다.

### ★ 규명 끝 — 코드는 레코드에 없다 (2026-08-14, 인게임 성공)

레코드에 코드가 있으리라 보고 `@(8,r8)` 을 썼다가 화면이 들쭉날쭉했다. **틀렸다.**

갈라낸 방법이 요점이다. `+8` 이 코드인지는 화면으로 확인할 방법이 없다 — 코드는
값이 제각각이라 폭이 이상해도 표가 틀렸는지 자리가 틀렸는지 모른다. 대신 **`+12`
가 바이트 길이(반각 1·전각 2)인지** 물었다. 값이 두 가지뿐이라 화면만 봐도 안다.
`폭 = @(12,r8) × 8` 로 구워 보니 **모든 글자가 똑같이 ２４ 안팎**이었다(간격 ~197px).
길이였다면 반각·전각이 갈렸어야 한다. 그러므로 레코드는 문자 정보가 아니라
**텍스처 사각형**이다.

객체 배치는 이렇다. 레코드 배열이 폭 배열 바로 앞에서 정확히 끝난다.

    obj+0x0054  레코드  25글자 × 320 (= 20크기 × 16B)
    obj+0x1F94  폭 배열 (크기별)        ← 루프의 `@r9`. 글자와 무관하니 고정폭이었다
    obj+0x1FF4  현재 인덱스
    obj+0x1FFC  ★ 코드 배열 포인터 (u16)
    obj+0x2004  글자 수

코드는 **별도 u16 배열**에 있고, 엔진 자신이 여섯 군데에서 같은 관용구로 읽는다
(`0x100033BE`·`0x100033EE`·`0x100031C4`·`0x10002F54`·`0x100031F8`·`0x10003D12`).

    mov.l  @(0x1FFC,obj),r0    ; 코드 배열
    shll   idx                 ; ×2
    mov.w  @(r0,idx),r1        ; u16 코드
    extu.w r1,r1
    shad   #-12,r1             ; 상위 니블로 분류 → **cp932 그대로**다

훅 자리에 `r10`(객체)·`r11`(인덱스)이 다 살아 있어서 스텁이 직접 꺼낸다. 단
`add #1,r11` 은 **코드를 읽은 뒤에** 둬야 한다 — 먼저 올리면 한 글자씩 밀린다.

### 하위표 우선순위 — 디스크 여유가 곧 품질이다

익스텐트 여유가 1,024B 뿐이라 하위표는 두 장이다. 그래서 **어느 페이지에 주느냐**가
품질을 정하는데, 처음엔 "폭 종류가 많은 순"으로 줬다가 URL 용 ASCII 페이지가 한 장을
가져갔다. 정작 공백이 든 페이지가 대표값으로 뭉개져 **공백 9 → 13, `。` 10 → 13**
이 됐다. 본문에서 １９,０００번 나오는 공백이 ２１７번 나오는 URL 에 밀린 것이다.

지금은 공백이 든 페이지와 전각 숫자·라틴이 든 페이지에 준다 — 가변폭으로 얻는 것이
거기 다 있다. 한글 페이지(`0x9B`·`0xE1`~`0xE3`·`0xED`·`0xEE`)는 전부 ２２ 단일값이라
직접값 한 바이트로 끝난다.

### ★ 다시 막혔다 — 코드 배열은 이 객체에 없다 (2026-08-14)

인게임에서 한글 폭이 ２２·２４·４０ 어느 값이든 **화면이 꿈쩍하지 않았다.** 표도
스텁도 훅도 디스크 실물에서 확인했는데도 그랬다. 그래서 폭을 눈금자 삼아 코드를
화면에서 직접 읽어냈다 — 페이지 번호의 두 비트씩을 ８/１６/２８/４０px 로
부호화해 네 판을 구웠다.

    한글 페이지(0x9B·0xE1~0xE3·0xED·0xEE)만 40 → 변화 없음
    모든 페이지 40                          → 전부 벌어짐   (표는 탄다)
    바이트를 뒤집어 0xB0                     → 변화 없음
    눈금자 4판                              → 상위 바이트가 **항상 0**, 글자마다 같음

즉 `@(0x1FFC,r10)` 에서 읽히는 것은 문자 코드가 아니다. `+0x1FF8` 로 옮겨 봤더니
**인게임에서 죽었다** — 포인터조차 아니다.

레코드 채우는 루프(`0x10003AC2`~`0x10003B3C`)가 답을 줬다.

    0x10003AD4  jsr @r2         글꼴 객체 vtable+64 → 글자별 16B **메트릭 배열**
    0x10003B0C  네 워드를 그대로 복사 → obj+84 + 글자*320 + 변형*16
    0x10003B3C  obj+0x1F94 + 변형*4 = 폭   vtable+84 를 **문자열당 한 번** 호출

레코드는 글꼴이 준 메트릭이고 폭은 문자열 전체에 한 번 정해진다. **문자 코드는
이 객체에 없다.** `0x1FFC`·`0x1FF4`·`0x2004` 를 쓰는 함수들은 기준을 `-4` 해서
쓰므로 애초에 **다른 객체**였다. 그 객체를 그리기 루프에서 어떻게 얻는지가
다음 과제다 — `*(r10+0x1FE4)` 가 유력하다(루프가 매 글자 그 포인터를 넘긴다).

또 하나 남은 길: 폭이 `vtable+84` 한 번으로 정해지므로, **글꼴 객체가 글자별
폭을 돌려주게** 만드는 쪽이 더 자연스러울 수 있다. 레코드 `+12` 가 이미 ２４ 인
것도 메트릭에 폭 자리가 있다는 뜻이다.

### 실패한 대안 — 코드를 찾지 않고 메트릭에 폭을 싣기 (2026-08-14)

그리기 루프에서 코드 배열을 되찾는 대신, 코드가 아직 `r11` 의 문자열 포인터로
살아 있는 **레코드 생성 시점**에 폭을 계산하는 경로를 구현해 보았다.

    0x10003AB6  @r11 의 Shift-JIS 첫째·둘째 바이트로 폭 표 조회
                계산한 폭을 아직 비어 있는 로컬 `@(0,r14)` 에 보관
    0x10003B18  원래 메트릭 +12 대신 보관한 폭을 글자별 레코드 +12 에 복사
    0x100035A8  그리기 폭을 이번 레코드 +12 에서 읽음
    0x100035B4  펜 전진폭도 이번 레코드 +12 에서 읽음

로컬 `+0` 은 이 구간에서 쓰이지 않고, 뒤의 `0x10003BB2` 호출이 출력 슬롯으로
재사용하기 전에 폭 복사가 끝난다. `0x10003AB6` 에 원래 있던 `vtable+64` 호출도
스텁 안에서 그대로 실행했다.

표는 첫 바이트 디스패치 ２５６B와 Shift-JIS 하위표 두 장으로 구성했다. ASCII는
첫 표에서 폭을 직접 돌려주고 리드 바이트만 하위표로 보냈다. 스텁 ６８B와 표
７６８B를 합친 ８３６B는 디스크의 １,０２４B 여유 안에 들어갔고, 생성한 SH4
분기와 대표 문자 폭도 정적으로 검증됐다.

하지만 **인게임에서는 실패했다.** 따라서 구현 코드는 제거하고 `font_variable`도
`false`로 되돌렸다. 정적 가정 가운데 적어도 하나가 틀렸다. 다음 조사에서는
아래를 각각 이진 탐침으로 분리해 확인해야 한다.

  * `r11` 이 이 시점에도 실제 Shift-JIS 글자 시작을 가리키는가
  * `@(0,r14)` 값이 `0x10003B18` 까지 보존되는가
  * 레코드 `+12` 가 그리기 호출의 폭으로 실제 소비되는가
  * `0x10003558` 루프와 `0x10003AC2` 레코드 생성이 같은 화면 경로인가

실패한 빌드의 설정 이름은 `"metric"` 이었지만 현재는 지원하지 않는다.

### ★ 라이브 조사 — Flycast 메모리를 직접 뜯었다 (2026-08-14)

굽고-보고 반복을 끊으려고 에뮬레이터를 살아 있는 채로 들여다봤다. 그동안 정적
분석과 화면 관찰로만 갈랐던 것을 라이브 메모리로 직접 확인했고, **막힌 벽의 정체가
달라졌다.**

도구는 [tools/dcgdb.py](../tools/dcgdb.py) 와 Flycast `flycast.lua` 다.
이 빌드 Flycast 2.6 은 `Debug.GDBEnabled` 를 켜도 **GDB 스텁이 실제로는
빠져 있다**(포트가 안 열린다). 대신 Lua 스크립팅이 있어서, `flycast.lua` 를
명령 서버로 만들어 메모리 read/write/scan · 버튼 입력 · 스크린샷을 원격으로
돌렸다. 명령은 `lua_cmd.txt` 로 넣고 결과를 `lua_out.txt` 로 받는다.

  * **물리 RAM 은 `0x8C000000`(P1)** 로 통째로 읽힌다. 게임 포인터(va)는
    `0x00xxxxxx`·`0x0Cxxxxxx` 대이고 **va→phys 는 MMU 페이지 매핑이라 선형이
    아니다.** 그래서 유출한 포인터 *값*을 물리 주소로 되돌리려면 페이지 테이블이
    필요하다 — self-ref store 유출이 안 잡힌 진짜 이유다(위치==값 이 성립 안 함).
  * 화면 텍스트의 cp932 코드는 `(lead<<8|trail)` **u16 리틀엔디언**으로 메모리에
    있다. codepage 역매핑으로 스캔·해독이 된다.

**확정 1 — 훅 `0x100035B4` 는 인게임 대사 그리기에 실제로 실행된다.**
살아 있는 대사창이 떠 있는 상태에서 이 자리 6워드를 라이브로 덮어썼더니 **대사
글자가 사라졌다.** 원본 6워드는 `HOOK_ORIG`(`6492 7B01 51AD 341C 52AC 3428`)와
정확히 일치했다. 즉 훅 위치는 맞고, 디스크 빌드가 안 먹힌 것은 **훅 자리가
아니라 스텁이 코드를 잘못 짚기 때문**이다.

**확정 2 — u16 코드 배열은 메뉴 엔진 전용이다.** 타이틀 세이브 메뉴에서는
완전한 객체(phys `0x8C600000`)를 찾아 `obj+0x1FFC` 의 u16 코드 배열 25글자를
전량 해독했다 — `방향_버튼_위아래로_항목을_고르고_좌우로_바꿉`, 화면과 일치.
**그런데 인게임 대사·선택지에서는 같은 u16 배열이 RAM 어디에도 없다.** 대사
텍스트는 raw(lead-first) SMF 원본 버퍼로만 잡힌다(`0x8C857552` 등). 선택지
`받을까` 도 raw 로만 잡혔다.

그러므로 문서가 내내 쫓던 "코드는 별도 u16 배열"은 **커맨드/메뉴 엔진의
이야기였고**, 인게임 대사(TRFSTRINGS 그리기 루프)는 코드를 그렇게 얻지 않는다.
`0x1FFC` 를 인게임 대사 객체에서 읽으려던 시도가 번번이 어긋난 근본 원인이다.

**남은 벽.** 그리기 루프가 코드를 얻는 경로는 여전히 미규명이다. 라이브
유출이 정석인데 두 가지가 겹쳐 막았다 — (가) 인게임 대사창은 **한 번 찍히면
정적**이라(선택지·커서와 달리 재렌더가 없다) 훅이 재실행되는 순간이 대사가
*타이핑되는 그 몇 프레임*뿐이다. (나) va→phys 가 비선형이라 유출값 해석에
페이지 테이블이 필요하다. **다음 수는 `flycast.lua` 의 vblank 콜백에 자동
유출기를 넣어**, 대사가 타이핑되는 프레임마다 `r8`·`r9`·`r10`·`r11` 을 고정
스크래치(코드에 리터럴로 박은 phys 주소)에 적재하고 로그로 뽑는 것이다. 폭
배열을 라이브 poke 해도 화면이 안 변한 것도 같은 결의 함정이었다 — 폭은 렌더
*전에* 한 번 세팅되고 정적 대사창은 다시 그리지 않으므로, poke 는 다음 렌더가
있어야만 반영된다.

### ★ 자동 유출기를 만들었다 — 그런데 다이나렉이 못 문다 (2026-08-14)

유출기는 [tools/vwleak.py](../tools/vwleak.py) 가 생성한다. 훅 12바이트를
`mov.l @(4,pc),r0 / braf r0 / nop / nop / .long 거리` 로 바꿔 RAM 스텁으로 뛰고,
스텁이 매 글자 `r10/r9/r11/r8` 을 고정 슬롯에 남긴 뒤 원래 훅 코드(폭·자간·보정·
인덱스)를 재현하고 훅 다음(`0x8CCAB5C0`)으로 braf 복귀한다. SH4 를 캡스톤으로
되읽어 분기 거리까지 정적 검증했다.

**그런데 인게임에서 리셋됐다.** 처음엔 스텁의 링버퍼가 미초기화 카운터로 범위 밖
store 를 내는 줄 알고 링버퍼를 뺐지만, 단순화한 스텁도 리셋을 냈다. 반면 **첫
실험에서 훅을 분기 없는 명령(`mov #24,r4`)으로만 바꿨을 때는 리셋이 없었다**
(글자만 사라졌다). 그러므로 원인은 스텁 로직이 아니라 **Flycast 다이나렉이 RAM
빈 영역(`0x8CFE0000`)으로의 braf 분기 타깃을 유효 코드로 못 잡는 것**이다.

두 갈래로 푼다. (1) 스텁을 TRFSTRINGS `.text` 케이브(이미 코드 페이지)에 두면
다이나렉이 코드로 인식할 공산이 크다 — 단 `.text` 꼬리에 문자열 데이터가 붙어
있어 케이브가 좁을 수 있으니 라이브 스캔이 필요하다. (2) emu.cfg
`Dynarec.Enabled = no` 로 인터프리터로 돌리면 자기수정·임의 분기가 안전하다 —
WinCE 타이틀이라 느리지만 조사에는 충분하다. `vwleak.py` 는 `stub_phys` 를
인자로 받으므로 (1)은 주소만 바꾸면 된다.

또 하나: **인게임 대사창은 한 번 찍히면 정적**이라 유출은 대사가 *타이핑되는*
프레임에만 일어난다. 스텁을 걸어 두고 고정 슬롯을 폴링하면 그 순간 값이 잡힌다.

### ★ 인터프리터로도 리셋 — 라이브 인젝션을 접는다 (2026-08-14)

`Dynarec.Enabled = no` 로 인터프리터에서 다시 걸었더니 **똑같이 리셋됐다.** 그러므로
원인은 다이나렉이 아니다. 라이브로 훅을 `braf` 스텁으로 바꾸는 것 자체가 이
환경(Flycast + WinCE + SH4)에서 불안정하다 — 짐작 가는 것은 `poke16` 6번이
비원자적이라 게임이 반쯤 패치된 훅을 실행하는 레이스이지만, Flycast Lua 에 게임을
멈출 `pause`/`resume` API 가 없어(있는 것은 `flycast.state` 테이블뿐) 원자적 패치를
못 한다. **라이브 코드 인젝션 접근 자체를 접는다.**

이어서 **코드 인젝션이 전혀 없는 관찰 기반**(메모리 읽기만)으로 돌렸다. 대사
"아・・코토리도 돌아왔다。" 의 raw SMF 버퍼는 두 벌 찾았다 — SMF 원본
(`0x8C857552`대)과 복사본(`0x8C77E958`대, 앞 `+0x10` 에 `03 00 00 00 … 43 00 44 00
1C 00 00 00` 꼴 헤더). 그런데 **그 버퍼를 가리키는 포인터가 phys 스캔에 안
잡힌다**(P1·P0 형식 모두 0건). 게임 포인터가 va 형식인데 **va→phys 가 MMU 페이지
매핑이라 비선형**이어서다. 관찰 기반도 결국 같은 벽이다.

**세 벽이 겹친다:** (1) va↔phys 비선형 — 유출·추적한 포인터를 물리로 못 되돌린다,
(2) 라이브 braf 인젝션이 리셋, (3) 인게임 대사창이 정적이라 훅 재실행 창이 좁다.

### ★★★ 벽을 넘었다 — 코드는 obj+0x3C 노드 리스트에 있다 (2026-08-15)

순수 관찰(메모리 읽기만, 인젝션 0)로 **인게임 대사 객체를 통째로 찾아냈다.**
대사 "아・・코토리도 돌아왔다。" 를 예로:

  1. 대사 텍스트의 raw SMF 복사본을 RAM 에서 찾고, 그 **바로 뒤에 16바이트 노드
     배열**이 붙어 있는 것을 발견했다. 각 노드는

         +0  u16 code      ★ 문자 코드 (cp932 (lead<<8|trail), 반각은 바이트)
         +4  u32 len       전각 2 · 반각 1
         +8  u32 self_va   자기 노드의 va (self-pointer)
         +12 u32 prev_va   앞 노드의 va

     노드 code 를 codepage 역매핑으로 풀었더니 `ee5d`(아) `8145`(・) `8145`(・)
     `eeef`(코) `eef2`(토) `eea8`(리) `ee50`(도) `8140`(공백) `ed8f`(돌)… —
     **화면 대사와 정확히 일치**했다. 문자열마다 이 노드 리스트가 하나씩 있다.

  2. 노드의 self-pointer 로 **이 힙 청크의 va↔phys 오프셋을 도출**했다:
     `phys = va + 0x8C014FE8`. (MMU 페이지 단위라 청크마다 다르지만, 한 청크
     안에서는 선형이다.)

  3. 노드 리스트 head 를 가리키는 외부 포인터를 스캔해 **대사 객체**(예로 phys
     `0x8C95844C`)에 닿았다. 레이아웃:

         obj+0x3C  노드 리스트 head       ★ 코드가 여기 매달려 있다
         obj+0x44  글자수 (이 예에서 13)
         obj+0x54  레코드 배열 (0,0,23,23 … = 텍스처 사각형, 문서의 "obj+84"=0x54)

**그러므로 문서가 내내 쫓던 `obj+0x1FFC`(코드 배열)·`obj+0x2004`(글자수)·
`*(r10+0x1FE4)` 는 이 인게임 대사 객체에 없다** — 그 오프셋들은 커맨드/메뉴 엔진
객체의 것이었다. 실제 인게임 대사 코드는 **`obj+0x3C` 의 노드 리스트, 노드 `+0` 의
u16** 이다. "코드가 이 객체에 없다"(2026-08-14)는 **틀렸다** — 노드 리스트를 못 봤을
뿐이다.

### 그래서 가변폭 훅은 어디에 거나

그리기 루프(`0x100035B4`)는 `r8`=레코드(obj+0x54), `@r9`=폭(고정)만 읽고 code 를
안 읽는다. 폭은 렌더 *전에* 레코드 생성 시 한 번 정해진다(문서: `vtable+84`,
문자열당 한 번). 따라서 **가변폭 훅의 정공법은 레코드 생성 루프
(`0x10003AC2`~`0x10003B3C`)에서 노드 code 로 폭을 정하는 것**이다 — 실패했던
"metric" 접근과 같은 자리이지만, 이번엔 **code 소스가 `obj+0x3C` 노드 리스트임이
실측으로 확정**됐다. 이전 "metric" 실패는 code 를 `r11` 문자열 포인터나 레코드
`+12` 에서 찾으려던 잘못된 가정 때문이었다. 다음 빌드는 노드 리스트에서 code 를
읽어 폭표를 조회하도록 훅을 짠다. (라이브 검증은 인젝션이 리셋을 내므로 못 하지만,
디스크 빌드 훅은 로드 시 이미 코드라 그 문제와 무관하다.)

### ★ 정적 분석 — obj 오프셋과 구현 경로 확정 (2026-08-15)

라이브 관찰로 잡은 구조를 정적 역어셈블로 검증하고 훅 경로를 확정했다.

**레코드 빌드 함수 `0x100038D0`** (SetText 후반). 핵심 자리:

    0x10003918  mov.l 0x10003a70,r9      r9 = 글꼴 객체 전역(0x1001D16C, TRFSTRINGS)
    0x1000395c  mov.l @(60,r8),r12       r12 = *(obj+0x3C) = 노드 리스트
    0x10003984  mov.l @r12,r12           노드 순회 (링크드리스트)
    0x10003aec  mov #84,r12 · add r8,r12 레코드 배열 = obj+0x54
    0x10003af4~ 메트릭(글꼴이 준 16B)을 레코드에 복사 — code 안 봄
    0x10003b32  mov.w 0x10003b66,r2      r2 = 0x1F94
    0x10003b3c  mov.l r0,@r3             폭배열[변형] = obj+0x1F94+변형*4 = 폭(고정)

리터럴로 **obj 오프셋을 확정**했다 — `+0x1F94`(폭배열)·`+0x1FF4`·`+0x2004`·
`+0x1FEC`·`+0x2014` 가 실제로 쓰인다. 즉 문서가 예전에 적은 그 오프셋들은 맞았고,
막혔던 것은 `+0x1FFC`(코드 배열)라는 **없는 필드**를 찾았기 때문이다. 진짜 code 는
`obj+0x3C` 노드 리스트에 있다.

**글꼴 객체 vtable(`0x1000DF80`, TRFSTRINGS .rdata)** 은 slot 4~8·15~20 이 전부
같은 accessor(`0x10009268` 등)라, `vtable+64`(slot16)는 code→메트릭 *변환*이
아니라 단순 accessor 였다. 실제 code→메트릭은 레코드 빌드 함수가 얽어 쓰는 여러
로컬 객체(`@(44,r14)` 등) 쪽이라 정적만으로 끝까지 못 짚었다 — 하지만 **가변폭엔
그 내부까지 필요 없다.**

**구현 경로 (vwstub.py 재작성 방향).** 그리기 루프 훅(`0x100035B4`)에서 `r9` 가
폭배열 주소(`obj+0x1F94`)이므로 —

    obj      = r9 - 0x1F94
    nodelist = *(obj + 0x3C)
    node     = nodelist 를 글자 인덱스(r11)만큼 링크 따라간 노드
    code     = *(node + 0)          u16 (lead<<8|trail)
    폭       = 폭표[code]

로 **그리기 시점에 code 를 얻는다** — 고 생각했으나, 라이브로 노드를 더 파 보니
**그 경로가 막혔다.**

### ★ 막힌 진짜 이유 — 노드 인덱스 ≠ 글자 인덱스 (2026-08-15)

라이브 검증 결과:

  * `obj+0x3C` 는 노드 자체가 아니라 **리스트 헤더**(sentinel)다. 헤더 바로 뒤
    `+0x20` 부터 노드가 16B 로 늘어선다. 노드 = `+0 u16 code · +4 len · +8 self_va ·
    +12 prev_va`.
  * "아・・코토리도 돌아왔다。" 를 헤더+0x20 부터 16B 씩 읽으니 `아 ・ ・ 코 토 리 도
    (공백) 돌 아` **10글자는 물리 연속**이었다. 그런데 **11번째부터 `+0x150` 으로
    점프**하고(`node[9].+8 = 0xa4` 로 링크가 끊긴 것처럼 보인다), 물리 연속이 깨진다.
  * 즉 노드 리스트에는 **그려지지 않는 토큰(마크업·줄 노드 등)이 섞여** 있어
    ([MTG-TIMING.md](MTG-TIMING.md) 의 "마크업은 세지 않는다"), **노드 인덱스와
    그리기의 글자 인덱스(`r11`)가 어긋난다.** 그리기 훅에서 `node[0] + r11*16` 으로
    글자를 직접 짚을 수 없다.

그리고 **글꼴 객체 `vtable+64`(`0x10009268`)는 단순 accessor** 였다 —
`mov.l 상수,r0 / rts`, 메트릭 배열 *주소*만 돌려준다. 그러니 code→메트릭 변환은
이 slot 이 아니라 그 앞의 다른 함수에서 일어나고, 레코드 빌드 함수가 얽어 쓰는 여러
객체(글꼴 전역 `0x1001D16C`, 로컬 `@(44,r14)` 등) 사이에 있어 정적만으로 끝까지 못
짚었다.

**그래서 남은 마지막 관문**은: 엔진이 **노드 리스트(전체 토큰)를 순회해 레코드/메트릭
배열(글자 인덱스)로 접는 그 함수**를 짚는 것이다. 거기가 노드 code 와 글자 인덱스가
동시에 살아 있는 유일한 자리이고, code→폭 훅을 걸 곳이다. 후보는 (a) 레코드 빌드
함수(`0x100038D0`)가 부르는 code→메트릭 변환 메서드, (b) 노드 code(`+0` u16)를
읽는 명령(`mov.w @Rn,Rm` 뒤 상위 니블 분류)을 정적 검색으로 찾기. 이 자리를 잡으면
`vwstub.py` 를 노드 code→폭표로 재작성 → 빌드 → 인게임 확인으로 간다.

**확정된 사실 요약** (다음 세션 출발점):
- 대사 obj: `+0x3C` 노드 리스트 헤더 · `+0x54` 레코드(글자 idx) · `+0x1F94` 폭배열(변형별 고정)
- 노드: `+0 u16 code`(cp932) · `+4 len` · `+8 self_va` · `+12 prev_va`, 헤더+0x20 부터
- 노드 idx ≠ 글자 idx (마크업 토큰 섞임) → 그리기 훅에서 직접 인덱싱 불가
- 라이브 인젝션은 리셋(다이나렉·인터프리터), va 역참조 peek 는 에뮬 크래시 → 순수 읽기만 안전
- va↔phys 는 청크별 선형(노드 self_va 로 오프셋 도출), 청크마다 값이 다름

### ★ 실현 가능한 구현 경로 — 토크나이저에서 폭을 미리 계산 (2026-08-15)

노드 순회를 포기하고 **code 의 원천**을 짚었다. 토크나이저(2바이트 문자 처리):

    0x10007800  mov.b @r9,r2          r9 = 문자열 커서, r2 = 리드바이트
    0x1000780C~ 리드바이트 판정 (0x81~0x9F · 0xE0~0xEF)
    0x10007834  mov.b @(1,r9),r0      트레일바이트
    0x1000783a  shll8 r4              리드 << 8
    0x1000783c  or r1,r4             ★ r4 = (lead<<8)|trail = code
    0x10007840  mov #2 → @(12,r14)    len = 2
    (그 뒤 노드 할당 → 노드+8=code · 노드+12=len, 리스트에 append)

**토크나이저 노드는 `+8 code · +12 len`** 으로, 라이브에서 본 그리기 노드
(`+0 code`)와 구조가 다르다 — 토큰 노드가 뒤에 그리기 노드로 변환되는 다중 리스트
파이프라인이다. 굳이 그 변환을 다 따라갈 필요 없다.

**경로:** `0x1000783C`(code 가 `r4` 에 살아 있는 자리)에서 **폭표를 조회해 글자
순서 폭배열에 쌓고**, 그리기 루프 `0x100035B4` 에서 `@r9`(고정폭) 대신 **그 배열을
글자 인덱스로 읽는다.** 토크나이저와 그리기가 둘 다 글자 순서로 진행하므로(마크업만
빠짐 — 토크나이저는 2바이트 문자 분기에서만, 그리기는 `r11` 로), **글자 카운터만
맞추면 노드 idx≠글자 idx 문제를 통째로 우회**한다. 노드 리스트 순회도, 청크 점프도,
va↔phys 도 필요 없다.

남은 설계: (1) 글자 순서 폭배열의 저장 공간(obj 의 미사용 영역 or 새 섹션의 고정
버퍼 — 한 창 최대 25글자×여러 줄), (2) 토크나이저 글자 카운터와 그리기 `r11` 의
정합(반각도 폭배열에 쌓아야 하면 `0x10007BC4` 반각 분기에도 훅), (3) 두 훅을
`vwstub.py` 에 얹기. 반각 금지 규칙([MTG-TIMING.md])대로 본문이 전부 전각이면
2바이트 분기만 훅하면 되어 카운터가 단순해진다.

### ★★★★ 진짜 답 — obj+0x1FFC 코드 배열은 실재했다 (2026-08-15)

토크나이저까지 갈 필요도 없었다. **그리기 경로가 obj 의 u16 코드 배열을 인덱스로
직접 읽는다.** `0x10003380` 함수(그리기 인덱스 관리):

    0x100033aa  mov.w 0x10003468,r3   r3 = 0x1FF4
    0x100033b2  add r3,r5             r5 = obj + 0x1FF4  (인덱스 카운터 주소)
    0x100033b4  mov.l @r5,r4          r4 = 인덱스
    0x100033bc  shll r4              r4 = 인덱스*2
    0x100033be  mov.w 0x1000346e,r0   r0 = 0x1FFC
    0x100033c2  mov.l @(r0,r8),r0    ★ r0 = *(obj+0x1FFC) = u16 코드 배열
    0x100033c4  mov.w @(r0,r4),r1    ★ r1 = 코드배열[인덱스]  (평면 배열, 순회 불필요)
    0x100033ca  shad #-12,r1         상위 니블 분류 (cp932 리드바이트)
    0x100033d0  mov.l @r5 … add #1   인덱스++ (obj+0x1FF4)

즉 **`obj+0x1FFC` 는 u16 코드 배열 포인터, `obj+0x1FF4` 는 인덱스**다. 노드 리스트
(`obj+0x3C`)는 토크나이저·타이밍용이고, **그리기는 이 평면 코드 배열을 쓴다.**
문서가 예전에 `obj+0x1FFC` 를 코드 배열로 지목한 것은 **처음부터 옳았다.**

**그러면 2026-08-14 의 라이브 실패는 왜?** 그때 `stub_code` 는 `obj` 를 `r10` 으로
가정했다(`OBJ_REG=10`). 하지만 obj 는 폭배열을 가진 그 객체이고, 그리기 루프에서
`r9` 가 폭배열 주소(`obj+0x1F94`)이므로 **`obj = r9 - 0x1F94`** 다. `r10` 은 obj 가
아니라서 `@(0x1FFC,r10)` 이 엉뚱한 값(상위 바이트 항상 0)을 읽었고, 그래서 폭을
어떻게 바꿔도 화면이 안 변했다. **훅 자리도 표도 다 맞았는데 obj 레지스터 하나가
틀렸던 것이다.**

### ★ vwstub.py 수정 — 이걸로 끝난다

그리기 루프 훅(`0x100035B4`)의 스텁을 이렇게 고친다:

    obj   = r9 - 0x1F94              (add #-… 또는 상수 빼기)
    idx   = *(obj + 0x1FF4)          (또는 루프의 r11 — 둘이 같아야 한다)
    code  = *(obj + 0x1FFC) 의 u16[idx]    (mov.l @(0x1FFC,obj) → mov.w @(idx*2,arr))
    폭    = 표[code]                 (기존 페이지맵/하위표 그대로)

기존 `stub_code` 골격(페이지맵→하위표 조회, `bsrf` 사슬, `_check_jump`)은 그대로
쓰고, **코드 읽기 앞부분만** `r10` → `r9-0x1F94` 로 obj 를 만들고 `+0x1FF4` 인덱스로
`+0x1FFC` 배열을 인덱싱하도록 바꾸면 된다. 노드 순회도, 토크나이저 훅도, va↔phys
도, 새 폭배열 버퍼도 필요 없다 — 훅 하나로 끝난다. (라이브 검증은 인젝션 리셋으로
못 하니 디스크 빌드 후 인게임 확인이다. `idx` 를 `r11` 로 할지 `obj+0x1FF4` 로 할지는
빌드해서 화면으로 가른다 — 값이 하나 어긋나면 글자가 한 칸씩 밀린다.)

### ★★★★★ 정정 — obj+0x1FFC 는 코드 배열이 아니었다 (2026-08-15, 인게임 검증)

위의 `obj+0x1FFC` 판단은 **틀렸다.** `r10+0x1FFC` 로 스텁을 짜 디스크 빌드해 라이브로
검증하니, 폭이 **글자가 아니라 위치(인덱스)에 따라** 정해졌다 — `가나다라` 를 시프트해도
회전해도 항상 **인덱스 6·7 이 좁게** 나왔다. 그리고 라이브로 객체를 직접 읽어 확정했다:

    obj+0x3C   = 노드 리스트 헤더 (예 UI 객체 0x0054198C)   ★ 진짜 코드가 여기
    obj+0x1FFC = 0x01A5D0D4  ← **모든 객체가 똑같은 공유값** (코드 배열 아님)
    obj+0x1FF4 = 0,  obj+0x2004 = 0

인게임 대사 객체든 UI 시스템 메시지 객체든 `obj+0x1FFC` 는 **같은 공유 테이블**을
가리킨다. 스텁이 이걸 코드 배열로 믿고 `[idx]` 로 읽으니, **텍스트와 무관하게 인덱스만
같으면 같은 폭**이 나온 것이다. `0x100033C2`(`mov.l @(0x1FFC,r8),r0`)는 코드 배열
읽기가 아니라 그 공유 테이블에서 상위 니블을 뽑아 **문자 분류**를 하는 자리였다 —
그걸 코드 소스로 오해한 것이 근본 실수다.

**그러므로 2026-08-15 의 "obj+0x3C 노드 리스트가 진짜 코드"가 처음부터 옳았다.**
`obj+0x1FFC` 로 우회하려던 시도는 전부 무효다. 스텁은 `obj+0x3C` 헤더에서 노드
리스트를 따라가 노드 `+0` 의 u16 code 를 읽어야 한다. (유저가 위치-의존 증상을
짚어 이 오류를 잡아냈다.)

### ★ 진단 스텁 — obj+0x3C 구조가 obj 종류마다 다르다 (2026-08-15)

스텁이 각 글자에서 읽는 (`head=*(obj+0x3C)`, `node`, `code`)를 고정 스크래치
(`0x8CFE0000`, P1 이라 va↔phys 무관)에 기록하고 폭은 24 로 고정하는 **진단
스텁**(`stub_diag`, `font_variable="diag"`)을 만들어 화면 밖에서 스텁 실제 동작을
읽었다. UI 로드 화면 결과:

    stub_diag (node = head + 0x20 + idx*16, 직접):
        head = 0x00538484 (모든 글자 동일)  ·  code 대부분 0000, 한글 ee?? 없음
    stub_diag2 (node = *(head) + idx*16, 한 번 역참조):
        code 여전히 0000/포인터 하위/ASCII 조각 — 한글 code 없음

즉 **UI 텍스트는 글자 code 리스트를 스텁이 닿는 경로에 안 가진다.** `obj+0x3C` 는
UI 에선 **head 포인터**(위젯 트리 앵커)이고, 노드를 아무리 따라가도 code 가 아니라
포인터/좌표/파일명 조각이 나온다. UI 시스템 메시지는 인게임 대사와 **렌더 방식이
근본 다르다**(위젯 기반) — **UI 는 이 가변폭 스텁의 대상이 아니다.** 스텁이 UI
렌더까지 잘못 잡아서 헛것을 읽고 "위치에 따라 폭이 바뀌는" 증상을 냈다.

그리고 **`stub_diag2`(`*(head)` 역참조)는 인게임 대사에서 리셋을 냈다.** 인게임
대사 객체의 `obj+0x3C` 는 UI 와 반대로 **노드 헤더 직접**(헤더+0x20 = node[0],
2026-08-15 확인)이라, UI 용 `*(head)` 역참조가 인게임에선 엉뚱한 주소를 읽어
죽는다. 즉 **`obj+0x3C` 노드 접근 방식이 obj 종류(인게임 대사 / UI / 메뉴)마다
다르다** — 이게 문제가 계속 미끄러진 근본 이유다.

**다음 순서 정정:** UI 부터 세우려던 계획은 폐기한다(UI 는 code 리스트가 없어
대상이 아니다). 인게임 대사만 대상으로, 인게임 `obj+0x3C`(노드 헤더 직접)에서
`stub_diag`(역참조 없는 첫 진단)로 노드를 읽어 code 가 실제 글자(`82xx` 라틴,
`ee??` 한글)와 맞는지 확정한다. 맞으면 노드 순회로 가변폭이 서고, 안 맞으면 인게임
노드도 헤더+0x20+idx*16 가정이 틀린 것이니 노드 링크 규칙을 다시 판다. 그리고
스텁은 인게임 대사 객체에서만 동작하도록 판별(예 `obj+0x2004` 글자수가 유효한지)이
필요하다 — 안 그러면 UI·메뉴 렌더까지 잡아 오작동·리셋을 낸다.

    한쪽만 켜면 넓게 그려졌다가 줄어들었다. 대사창도 클릭 대기 마커 등으로
    두 경로일 수 있다
  * **켜면 안 되는 자리가 있다.** 공용 경로를 켰더니 엉뚱한 화면이 바뀌었다

### ★★ 이름 토큰(`&主人公名前&`)의 폭 어긋남 — copy 훅이 토크나이저 노드 리스트를 읽는다 (2026-09-17)

**증상.** `&主人公名前&．도쿄에　사는…` 줄에서 이름 `타사카　츠요시` 안의 공백이 넓고,
`시` 가 눌려 `．` 이 `도` 에 덮였다.

**원인.** copy 훅(HOOK2 `0x10003AE6`)의 `stub_rec_x2` 가 `r11` = **치환 전 raw 줄
텍스트**를 1/2바이트로 파싱했다. PLOT.CB 엔 토큰이 `&主人公名前&`(12B) 리터럴로 들어
있으므로 `[&][主][人][公][名][前][&]` 7글자에 폭 `[ASCII ~21, 24×5(한자=폭표 밖→기본),
~21]` 을 쓰고, 그 7 레코드에 이름 7글자(namesep 공백 포함)가 그려졌다 → 이름 안 공백이
24(정상 9). 이름 길이가 7이 아니면 뒤 글자 전부가 밀린다.

**엔진 쪽 사실(정적 역어셈블).**
  * 토큰 처리는 렌더러 `0x100076DC`(폰트객체 메서드, r4=fontobj, r5=문자열)에 있다.
    `&`(`0x1000799C`)에서 `fontobj+612` 의 표(`arr[2k]`=치환문, `arr[2k+1]`=토큰 문자열,
    비교 함수 `*0x1001D050`)를 찾아 치환문을 `0x10007A28~` 루프에서 2바이트씩 emit 한다.
    `%..%`(`0x10007B2A`)·`@..@`(`0x10007B58`)는 노드를 만들지 않고, `$N`(`0x1000794E`)은
    len 0 노드를 만든다.
  * emit 된 글자는 **`fontobj+0x6C` 리스트**(`+0 head`, `+4 tail`)에 노드로 붙는다 —
    노드 `+0 next · +8 code(lead<<8|trail, 반각은 바이트) · +12 len(2/1/0)`. 치환문 경로도
    같은 리스트·같은 형식이고 `@(44,r8)` 글자수도 함께 센다. 리스트는 SetString 진입
    (`0x10007712~`)마다 비워진다. (8/15 의 대사 obj `+0x3C` "`+0 code`" 리스트와는 다른
    리스트다 — 그쪽은 마크업이 섞이고 청크가 끊겨 인덱싱 불가.)
  * copy 루프(`0x10003AE6~`) 자체는 문자열을 안 보고 폰트객체 vt[64] 메트릭을 복사할 뿐
    이며, 이 함수는 `0x10003918` 에서 `r9 = &글꼴전역(0x1001D16C)` 로 두고 HOOK2 까지
    안 덮는다.

**수정.** `stub_rec_x2` 가 `r11` 대신 `*(*r9)+0x6C` 의 head 부터 `next` 로 순회하며
len≠0 노드만 `code→폭표→rec.x2` 로 쓴다(`@(36,gbr)` 개수만큼). 새 훅·버퍼·절대주소
없음(스텁 124B, 표는 그대로 `mova`). 모든 토큰(`&主人公&`·`&名前&`·`&マフラー&`)과
어떤 이름 길이든 자동이고, raw 파싱 때 `@..@` 가 3글자로 세어지던 잠재 어긋남도 사라진다.
인게임 확인 완료(2026-09-17).

**남은 참고.** `．` 의 폭은 3(잉크 5)이라 뒤에 글자가 바로 오면 겹쳐 보일 수 있다 —
폭표(`Widths`) 값 문제로 별건.

### ★ 가이드북: 안내문은 가변폭인데 도시 설명은 고정폭인 이유 — 텍스트 클래스가 다르다 (2026-09-17)

**관찰.** 지도 화면 하단 안내문(`方向ボタン…`)은 프로포셔널로 그려지고, 같은 화면의 도시
설명(`guide3.msl`: 인구·면적 줄)은 전각 24px 고정 피치로 그려진다.

**구조.** 텍스트 클래스는 전부 TRFSTRINGS 가 구현하고(등록 테이블 `.data`), 각 화면 DLL 은
클래스 팩토리(TRFGUIDEMAP 에선 `0x100050dc`)에 **클래스명 문자열**로 객체를 만든다.
TRFGUIDEMAP 이 만드는 것: `CTRFMessage`/`ITRFMessage` ×5, `CTRFMsgput`/`ICustomMsgput` ×1,
`CTRFTXOut`/`ITRFTXOut` ×2, `CTRFContainer`·`CTRFMenuCursor`·`CTRFClipper`·`CTetran`·`CKitaVMS`.

  * **안내문 → `CTRFMessage`.** `0x10002ea4` 에서 create("CTRFMessage","ITRFMessage") 한 객체에
    `0x10002eac` 가 문자열을 `vt[20]` 으로 넘긴다. ITRFMessage vtable `0x1000d3c4`(270슬롯)의
    `[5]`(오프셋 20) = **`0x100038D0` = 레코드 빌드(SetText 후반, HOOK2 copy 루프 포함)**,
    `[30]` = **`0x100034FC` = 그리기 루프(HOOK 전진폭·HOOK3 DrawChar 래퍼)**. 즉 가변폭 훅
    세 개는 정확히 이 클래스의 SetText/draw 에 걸려 있다. (`0x1000d000`(193슬롯)에도 같은
    함수가 [114]/[139] 로 실려 있다 — 같은 객체의 다른 인터페이스 vtable.)
  * **도시 설명 → `CTRFMessageList` + `CTRFMsgput`/`CTRFTXOut`.** 가이드 페이지 함수는
    `CTRFContainer.vt[32]("SOZ")` 로 리소스를 열고 `vt[48]("guide3.msl","ITRFMessageList")` 로
    메시지 목록을 받는다(`0x10002e68`). 스폿 설명은 `guides.msl` 을 가리키는 16B 레코드 표
    (`0x144e4~`, 큐빅 사고의 그 표)로 같은 경로. 이 목록의 표시는 `ICustomMsgput`
    (`CTRFMsgput`, `0x1000142c`)·`CTRFTXOut` 이 맡는다.
  * **고정폭의 정체 = `CTRFTXOut` 이 안에 품은 `CTRFTextOut` 의 그리기.** (2026-09-18 정정:
    처음엔 `0x1001c980` 을 CTRFTXOut vtable 로 적었는데, 그 표는 QI 표가 `ITRFTextOut` 인
    **CTRFTextOut** 의 것이다. 등록 레코드 `.data 0x1013618c` → 생성자 `0x1000b19c`, 52B,
    최종 vtable `0x1001c9c8` = [0..2] QI/AddRef/Release + `[3]=0x1000970c [4]=0x10009b88
    [5]=0x10009bec [6..8]`.)
    - `CTRFTXOut` 등록 레코드 `.data 0x101360e8` → 생성 `0x1000a3c0`→`0x1000a3ec`(64B).
      vtable 둘: +0 `0x1000e0d4` = **ITRFTXOut 13슬롯** (`[5]=0x1000a068` 줄 추가
      (x,y,str,len) → 줄 리스트 +32, `[9]=0x1000a140` 표시 플래그 +60, `[10]=0x1000a27c`,
      `[12]=0x1000a00c` 줄 전부 삭제), +4 `0x1000e108` = **ITRFDrawObject** (`[3]=0x1000a148`
      Draw). 초기화 `0x10009f1c` 가 `TRFCreateInstance("CTRFTextOut",0,"ITRFTextOut",&+56)`
      로 내부 객체를 만든다.
    - Draw `0x1000a148` 은 줄마다 `내부->vt[5]`(= `0x10009bec`, `0x1000a1fa`/`0x1000a260`)
      를 부르고, `0x10009bec` 의 문자 루프가 폰트 DrawChar(`0x10009cda`, 폰트 vt 오프셋 52)
      를 부르면서 **전진폭을 2바이트 글자 `mov #24,r8`(`0x10009c56`) / 1바이트
      `mov #12,r8`(`0x10009c8e`) 로 상수 지정**한다. 폭표를 보지 않으니 글자마다 같은 칸이다.
      이 경로엔 훅 함수가 하나도 없다.

TRFSTRINGS 안의 DrawChar 호출 가운데 훅이 감싸는 건 CTRFMessage 의 2곳
(`0x10003584`·`0x100035ae`)뿐이다. 나머지: `CTRFSquareStr`(`0x10002854`·`0x1000970c`),
폰트 내부 아틀라스 빌드(`0x10007c64`·`0x10007df0`, vt `0x1000dbb4`), `CTRFTextOut`(위).

**따라서** 도시 설명(및 TXOut 을 쓰는 다른 UI 텍스트)에 가변폭을 주려면 `CTRFTextOut`
`0x10009bec` 의 전진폭 상수(`0x10009c56`/`0x10009c8e` 의 r8)를 폭표 조회로 바꾸는 **별도
훅**이 필요하다 — CTRFMessage 훅과 독립이고, 그 클래스는 `rec.x2` 파이프라인을 쓰지 않는다.

### 타이틀 VMS 메시지("메모리 카드에 접근 중입니다")도 같은 경로 (2026-09-18)

`CTRFTXOut` 을 만드는 모듈(= 전부 고정폭): ITEMMENU, KITACMDMENU, KITATITLE, SOUNDROOM,
