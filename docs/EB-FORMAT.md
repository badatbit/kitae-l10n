# EB(이벤트 바이트코드) ↔ SMF(문자열 테이블) 참조 방식 분석

분석일: 2026-08-05 · 대상: PLOT.CB 내 48개 EB/SMF 쌍 전체

## 결론: EB는 SMF를 바이트 오프셋으로 참조하지 않는다 → 번역문 길이 자유

**검증 방법** — 48개 EB 전체를 대상으로, 모든 바이트 정렬(u16/u32 × LE/BE)에서
EB 안의 값이 "실제 SMF 문자열 시작 오프셋 집합"과 일치하는 횟수를,
+7 시프트한 가짜 오프셋 집합(대조군)과 비교:

| 인코딩 | 실제 오프셋 일치 | 대조군 일치 | 비율 |
|---|---|---|---|
| LE u16 | 9,328 | 8,411 | 1.11 |
| BE u16 | 9,432 | 11,021 | 0.86 |
| LE u32 | 543 | 456 | 1.19 |
| BE u32 | 476 | 361 | 1.32 |

비율이 전부 ~1.0 = 우연 수준. 오프셋이 하드코딩돼 있다면 문자열 수(23,030)만큼의
초과 일치가 나와야 하지만 전혀 없음. 또한 `.STR` 테이블 자체에 오프셋 색인이 없어
(널 종료 문자열 나열뿐) 엔진은 로드 시 스캔으로 색인을 만들 수밖에 없는 구조.

**추가 방증**: `KAORU_2.EB`는 24바이트 스텁(헤더뿐)인데 짝인 `KAORU_2.SMF`엔 194개
문자열이 있음 → 문자열 소비는 인덱스/커서 기반으로 EB 외부(엔진/SCV)에서도 일어남.

### 번역 시 불변 조건 (안전 규칙)

1. **문자열 개수와 순서를 유지**하고
2. `.STR` 헤더의 총 크기 필드(u32 @4)와 CAB 엔트리 크기/오프셋을 재계산하면
3. **각 문자열의 바이트 길이는 자유롭게 변경 가능** (cp932 인코딩 유효성만 유지)

## EB 파일 구조 (2026-08-06 확정 — 48개 파일 전수 검증)

```
+0x00 u16 header_size (=0x0c)
+0x02 u16 version     (=2; 스텁은 0)
+0x04 u16 scene_count (= 씬 블록 개수. 아래 표의 길이)
+0x06 u16 tail_off    (꼬리 u32 배열 시작)
+0x08 u32 tail_size   (파일 끝 = tail_off + tail_size, 확인됨)
+0x0c u16 secA        (씬 블록 영역 시작 오프셋)
+0x0e u16 secB        (또 다른 섹션 오프셋)
+0x10 u16[scene_count]  ← **씬별 블록 오프셋 테이블**
        (48개 파일 전부에서 단조증가 + 파일 범위 내 = 검증 완료)
...   u16 테이블 (씬 블록 내부를 가리킴, 간격 4~10)
씬 블록: (u16 event_id, u16 code_offset) 쌍의 나열
        - 앞 5개는 **모든 씬 공통 고정 핸들러** 0xE8~0xEC
          (KOTORI_01에서 전 씬이 0x28bb/0x28ec/0x28f3/0x290d/0x2914로 동일)
        - 이후 event_id는 0x20부터 순차 = INI의 E00, E01, … 슬롯
바이트코드: 위 code_offset들이 가리키는 가변길이 명령 스트림
tail: u32 배열 (순차 증가 ID + 0 패딩 — 용도 미상)
```

- **씬 개수 주의**: `scene_count`는 INI의 씬 수보다 작거나 같다(48중 28개는 일치,
  나머지는 EB 쪽이 적음). 코드가 없는 씬(무비 전용 등)은 테이블에서 빠지므로
  **EB 씬 인덱스 ≠ INI 씬 번호**. 매핑에 주의할 것.
- **이벤트 개수 주의**: EB의 event_id 개수가 INI의 E## 항목 수보다 많다
  (예: KOTORI_01 씬#0 = 19개 vs INI P01S000 = 12개). INI에는 작성자가 주석을 단
  이벤트만 기록돼 있다.
- 예: KOTORI_01 씬#0 → 이벤트 0x20의 코드가 0x0A98. 그 지점에 22바이트 고정 레코드가
  반복되며, 필드에 2의 거듭제곱 비트마스크가 들어간다.
- `north01.msd`: `(id, offset, length)` 세그먼트 테이블 + 병합 정렬된 u16 시퀀스.
  세그먼트 오프셋들이 서로 연속(0x0f0a→0x139f→0x15a9…) — 메시지↔음성(P04) 매핑 추정, 미해석.
- 음성: `RESOURCE/WAV/0-7.CB`에 `aNNNN.p04` 약 5,900개 (희소 번호).

## 옵코드 해석 완료 (2026-08-06) — 화자 확정

### VM 위치

인터프리터는 KITAE.DLL이 **아니라** **`TRF/KITAHEGEL.DLL`**(`CKitaheGel`, image base 0x10000000)에 있다.
KITAE.DLL의 `EDL`/`Plot` 문자열은 서브시스템 조회용 이름일 뿐이었다.

| 항목 | VA |
|---|---|
| fetch/dispatch 루프 | `0x10005F34` |
| 옵코드 디스패치 테이블 | `0x100131B4` (.data) — 유효 옵코드 **0x01~0x9C, 156개** |
| 오퍼랜드 길이 테이블 | `0x10013428` (.data), 156바이트 |

명령 형식은 단순하다: **`u8 opcode` + `OPLEN[opcode]`바이트 리틀엔디언 오퍼랜드**.
루프가 그대로: `op=*pc; len=lentab[op]; operand=pc+1; pc=pc+1+len; handtab[op](gel)`.

### 번역에 필요한 옵코드

| op | 오퍼랜드 | 의미 |
|---|---|---|
| **0x6A** | u16 | **화자 지정** — `north01.sym` 그룹0(89개) 인덱스 |
| **0x6B** | u16 | **메시지 창 N 표시** (모드 0) |
| **0x6C** | u16 | **메시지 창 N 표시** (모드 2) |
| **0x73** | u16 | 메시지 창 N을 **선택지**로 표시 |
| **0x74** | u16 창, u16 슬롯 | 선택지 + 결과를 변수 슬롯에 기록 |
| 0x78/0x79 | u16 | VSC 컷 선택 (`0x4000|n`) |
| 0x85/0x87/0x89 | 20바이트 | KitaEvent 트랩 등록 (= 앞서 본 "22바이트 레코드") |
| 0x23~0x25 / 0x31 | u8/u16/u32 | 즉치 push / tail 데이터 테이블 읽기 |
| 0x01~0x0A | 각종 | 점프·조건분기 |

**0x6B의 오퍼랜드는 SMF 문자열 인덱스가 아니라 "창 인덱스"**이며, `MTG/<script>.SET`/`.WST`와
번호 체계가 같다.

### 검증 (3중)

1. **48개 EB 전부가 잘못된 옵코드 0건으로 디코드**되고 스트림이 정확히 `tail_off`에서 끝난다
   — 오퍼랜드 길이가 전부 맞지 않으면 불가능.
2. `max(창번호)+1 == MTG 창 개수`가 **46/47 스크립트**에서 성립. 모든 메시지 옵코드 앞에
   예외 없이 0x6A가 선행.
3. 화자↔음성 상관: 独白 1,958창 **전부 무음**, システム 170/170 무음, 説明 43/43 무음,
   主人公 749창 중 747 무음(주인공은 무음성). 반면 琴梨·鮎·梢·めぐみ·薫·葉野香·由子·
   ターニャ·陽子는 압도적으로 유성.
4. 오프닝 정답 재현: 창 0~8 = `文字, 琴梨, 陽子, 陽子, 琴梨, 陽子, 琴梨, 陽子, 琴梨` ✔

## 미해결 (번역 작업엔 지장 없음)

- 바이트코드 옵코드 셋 (0xa98 부근에 `85 00 00 XX ...` 반복 패턴 = 리소스 로드 추정)
- tail u32 배열과 msd의 정확한 용도
- 최종 확증은 redream 실기동 테스트로: 문자열 길이를 바꾼 패치 이미지가 정상 표시되는지
  (총 크기 유지 스왑 테스트면 디스크 리빌드 없이 섹터 패치만으로 가능)
