# MTG 문자 타이밍 (CTRFMsgTiming)

대사 한 글자 한 글자가 화면에 찍히는 시각이다. 음성 녹음에 맞춰 손으로 찍어
놓은 값이라, 번역으로 글자 수가 바뀌면 이걸 새로 만들어 줘야 한다.

정적 분석 대상: `TRF/TRFMSGTIMING.DLL`(컨테이너), `TRF/TRFSTRINGS.DLL`(소비자),
`TRF/MESSAGEOUT.DLL`(연결). 이미지 베이스 0x10000000.

## 형식

`MTG.CB` 안의 `<script>.SET` 은 CLSS 트리이고, 메시지 창마다 `CTRFMsgTiming`
레코드가 하나씩 있다. 페이로드는

```
u16 count                       // 표시 글자 수 + 1
u16 entry[count]
entry = (lip << 12) | duration   // duration 0..4095, lip 0..8
```

`duration` 은 **밀리초**다. 프레임도, 임의의 틱도 아니다.
`lip` 은 입 모양으로 `ITRFLipControll` 에 넘어간다. 0 = 다문 입 = 무음.

음성이 없는 창은 페이로드가 2바이트(`count == 0`)뿐이다.

> **주의** — 예전에 이 페이로드를 `u32 count + (u8,u8) 쌍`으로 읽었다. 길이가
> 우연히 맞아떨어져서 오래 들키지 않았다. 그 해석에서는 256ms 이상의 값이
> 전부 mod 256 으로 잘리는데, 하필 그 값들이 성우가 쉬는 구간이라 싱크를
> 맞추려는 시도가 전부 실패했다. 확인 방법: 상위 니블은 20만 항목 전체에서
> 한 번도 9 이상이 나오지 않는다(임의 비트라면 44%가 나와야 한다).

## 엔진 동작

`CMessageOut::OpenWindow`(MESSAGEOUT 0x10001524)가 창에서 `ITRFMsgTiming` 과
`ITRFWaveName` 을 꺼내 `CTRFMsgput::SetMessage`(TRFSTRINGS 0x100036D4)로
`(본문, 타이밍, 음성경로)` 를 넘긴다.

갱신 루프(TRFSTRINGS 0x10002F20)는 `GetTickCount()`(COREDLL ordinal 535)에
duration 을 **누적**해 마감 시각을 만든다. 누적이라 프레임 드리프트가 없다.

- 시작: `index = 0`, `deadline = now + d[0]`
- 매 프레임 `now > deadline` 이면 → `index++`, 입 모양 갱신, `deadline += d[index]`
- 렌더러는 정확히 `index` 글자를 그린다

따라서 **`entry[i]` 는 글자 i 를 찍기 *전에* 기다리는 시간**이고, 글자 i 는
시작 후 `sum(d[0..i])` ms 에 나타난다. 마지막 항목은 글자가 없는 종결자로,
마지막 글자 뒤의 여운이다(6,108/6,192 창에서 0).

줄바꿈은 항목을 소비하지 않는다. 창의 여러 줄은 별개의 SMF 문자열이지만 하나의
글자 열로 이어져 같은 인덱스를 쓴다. 인라인 마크업(`@S@`, `@P@`, `&主人公&`)은
그려지지 않으므로 세지도 않는다 — 별도 이벤트 배열이 같은 인덱스로 따라간다.

타이밍이 없으면 설정값(기본 100ms/자)으로 균등하게 찍는다.

## 음성과의 관계

**음성은 이 배열에 묶여 있지 않다.** `SetMessage` 가 확장자를 `.p04` 로 바꿔
`CTRFSoundRawFile` 을 열고 한 번 재생을 걸 뿐, 이후로 재생 위치나 완료 여부를
묻지 않는다. 싱크는 순전히 이 숫자들이 녹음에 맞게 찍혀 있어서 유지된다.

음성 포맷은 TRFSTRINGS 0x1000374C 에서 `wFormatTag=32(Yamaha ADPCM), 1ch,
18000Hz, 4bit` 으로 고정. 그래서 `voice_ms = 파일크기 * 2 / 18`.

검증 — 유성 창 6,103개 회귀: `samples = 17.67 * sum(duration) + 2,979`
(R² = 0.975). 기울기가 18에 붙고, 절편 ~166ms 는 앞뒤 여유다.

배열 길이가 글자 수와 어긋나도 죽지는 않지만 싱크가 망가진다.
짧으면 남은 글자가 프레임당 하나씩 쏟아지고, 길면 창이 끝나지 않는다.

## 재생성 규칙 (`kitae/build/mtg.py`)

원본은 특정 녹음에 대한 정렬이므로 다른 글자 수의 값을 *복원할* 수는 없다.
*재분배*만 가능하다. 누적 시각만 의미가 있으므로 재분배는 안전하다.

번역은 줄 단위로 관리하므로 **줄 경계는 원문과 번역이 같다.** 그래서 줄마다
원본이 쓰던 시간을 그대로 물려받는다 — 줄 시작·끝 시각이 원본과 정확히 같다.

줄 안에서는

1. 250ms 이상인 구간을 쉼으로 본다.
2. 쉼은 '침묵 + 그 글자 발음시간'이 합쳐진 값이므로, 보통 음절 시간(같은 줄의
   비-쉼 구간 평균)을 뺀 **침묵분만** 보존한다. 통째로 옮기면 새 칸이 받는
   발화 몫이 덧붙어 쉼이 길어진다.
3. 침묵을 뺀 나머지를 새 글자 수에 고르게 나누고, 침묵을 비례 위치에 얹는다.
4. 입 모양은 원본에서 비례 위치의 값을 가져오되, 쉼 칸은 0(다문 입)으로 둔다.

결과(KOTORI_01 창 1~4): 총시간과 줄 종료시각은 원본과 **정확히** 일치하고,
쉼 길이는 3% 이내로 유지된다.

## 엔진이 실제로 소비하는 항목 수 — 반각을 쓰면 안 되는 이유

`SetText`(0x10003BB2~0x10003BE6)는 **우리가 준 배열을 그대로 쓰지 않는다.**
`ITRFStrTimingImport::BuildTiming`(0x10007524)으로 텍스트를 파싱해 배열을 새로
만들고, 그것을 `SetTimingArray` 로 다시 넣는다. 값은 `newArray[j] = payload[j]`
로 순서 그대로 통과하고 **길이만 다시 정해진다.**

토크나이저(0x100076CC)가 타이밍 노드를 붙이는 자리는 셋뿐이다:

| 위치 | 언제 | 노드 |
|---|---|---|
| 0x100077C4 | 빈 줄이 아닌 **줄마다 한 번**, 루프 전에 | +1 |
| 0x100078C8 | **2바이트 문자**마다 | +1 |
| 0x10007BC4~0x10007C00 | **반각(1바이트) 문자** | **없음** |

리드바이트 판정은 표가 아니라 두 구간 하드코딩이다(0x1000780C~0x10007832):
`0x81~0x9F` 또는 `0xE0~0xEF`.

    실제 소비 항목 수  M = L + D      L = 줄 수, D = 2바이트 문자 수

글리프 인덱스는 글자당 하나씩 늘고(0x100033D0), `index >= M` 이 되면
0x10003220 의 `deadline += 1` 로 떨어져 **남은 글자가 프레임당 하나씩** 쏟아진다.

    싱크 조건  M >= G + 1  ⟺  H <= L - 1      G = 글리프 수, H = 반각 수

즉 **한 줄짜리 창은 반각을 하나도 못 쓰고**, 두 줄짜리는 하나까지다.
그래서 번역문은 전부 전각이어야 한다. 전각만 쓰면 `M = L + G` 라 원문과 똑같이
동작한다.

> 앞서 이 문서에 "항목을 바이트 단위로 소비한다"고 적었던 것은 **틀렸다.**
> `D = 바이트수 − 글리프수` 라서 증상 지점이 우연히 바이트 위치와 맞았을 뿐이다.

부수적으로 알게 된 것:

- 원본 데이터도 헤더가 `G + 1` 이라, **여러 줄 창에서는 원래부터 배열 끝을
  1~2칸 넘겨 읽는다**(커서에 경계 검사가 없다). 그 값은 마지막 글자 뒤의 대기로만
  쓰여 무해하고, 우리도 `G + 1` 을 쓰므로 원본과 동일하게 동작한다. 굳이 없애려면
  `G + L` 개를 쓰고 뒤를 0으로 채우면 된다.
- **한 줄에 그려지는 글자는 25개가 상한**이다(0x10007C30, 레코드 배열
  `obj+0x84`~`obj+0x213` = 25×16B). 넘는 글자는 토큰화는 되지만 그려지지 않는다.
- 펜 전진은 글리프 폭과 무관한 **고정 피치**다(0x100035B4~0x100035C8). 반각을 써도
  칸은 전각 하나를 차지한다 — 좁아 보이는 게 아니라 그림만 좁고 자리는 그대로다.

## 쉼의 자리 — 문장부호 맞춤

새 글자 수에 맞춰 쉼을 옮길 때 비례 위치에 그냥 놓으면 낱말 한가운데서 멈춘다
(`응. 아〈쉼〉침`). 성우가 쉬는 자리는 문장이 끊기는 자리이므로 번역문의
**문장부호 뒤**로 당긴다.

- 멈출 자리: `。．.、，,！!？?・…―` 뒤. 그리고 그런 기호 뭉치 **바로 앞**도
  인정한다 — `마지막이라〈쉼〉・・` 처럼 말줄임 앞에서 끊는 경우가 있다
- 닫는 기호 `』」）〉》”` 와 공백은 그 자체로 멈출 자리가 아니다. 넘겨서
  다음 글자 바로 앞에 세운다 — 공백은 보이지 않으므로 그 앞에서 멈추면
  화면상 어중간하다
- 마땅한 기호가 없으면 낱말 경계(공백)라도 쓴다
- 비례 위치에서 **±5칸** 안에서만 당긴다. 더 멀리 가면 쉼의 *시각*이 틀어져
  음성과 어긋난다
- 앞 쉼이 쓴 자리 다음(lo)과 뒤에 올 쉼들의 몫을 남긴 상한(hi)을 후보를 고를
  때부터 반영한다. 고른 뒤에 밀거나 자르면 하필 낱말 한가운데로 떨어지거나
  앞 쉼과 한 칸에 겹쳐 하나로 뭉친다

KOTORI_01 전량 기준: 어절 경계에 놓인 쉼이 73% → **96%** (낱말 한가운데
119개 → 17개). 겹쳐 뭉치던 것이 풀려 쉼 개수도 446 → 456으로 늘었다.
남은 17개는 ±5칸 안에 경계가 없는 경우다.

## 확인 도구

```
python -m kitae timingtest KOTORI_01 -w 1,2,3,4          # 원문 타이밍
python -m kitae timingtest KOTORI_01 -w 1,2,3,4 --built  # 빌드 결과
```
`work/timing.html` / `work/timing-built.html` 을 브라우저로 열면 음성과 함께
값 그대로 글자가 찍힌다. 에뮬레이터를 켜지 않고 싱크를 확인할 수 있다.
