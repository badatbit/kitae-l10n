# 시스템 텍스트 (DLL 안의 문자열)

메뉴·안내문·지명 같은 시스템 텍스트는 `.SMF` 처럼 리소스로 빠져 있지 않고
**DLL 의 `.data`/`.rdata` 에 NUL 로 끝나는 cp932 문자열**로 박혀 있다.
디스크 전체에 33개 모듈 1,944개.

도구: `python -m kitae uitext` (추출) → `translation/ui/<모듈>.json` →
빌드 때 `kitae/build/uipatch.py` 가 주입.

## 1. 추출 — 걸러 내기가 까다롭다

`.text` 에도 NUL 로 끊어 읽으면 cp932 로 해석되는 바이트열이 잔뜩 나오지만 전부
명령어다. 그래서 데이터 구간만 보고 글자 구성으로 한 번 더 거른다
(`kitae/core/pestr.py`).

두 번 데어서 배운 것:

- **전각 1자짜리도 뽑아야 한다.** "2자 이상"으로 걸렀더니 `月`, `日`, `Ａ`, `１`
  이 통째로 빠졌다. `８月　１日午前` 은 통짜 문자열이 아니라 엔진이 이 조각들을
  **조립**하는 것이었고, 시간대만 바꾸니 조립이 어긋나 `1 1전오` 가 나왔다.
- **앞에 붙은 이진 바이트를 넘겨야 한다.** 포인터 여러 개 뒤에 문자열이 붙어
  있는 경우가 있다(`04 25 01 10` + "１番目のデータを…", 심하면 포인터 5개
  20바이트). 시작점을 32바이트까지 밀어 가며 다시 본다.

## 2. 주입 — 자리를 넘길 수 없다

문자열 테이블이 없으므로 **있던 자리를 덮어쓴다.** 정렬 패딩까지 쓸 수 있어
`avail`(원문 + 뒤따르는 0, 8바이트까지)이 실제 한도다.

넘치면 `kitae/build/relocate.py` 가 옮긴다:

1. 자리에 들어가는 것은 제자리에, 넘치는 것은 남은 빈칸으로 옮기고 포인터를
   고쳐 쓴다.
2. 빈칸이 잘게 흩어져 실패하면 **소유 공간 전체를 비우고 다시 깐다**(`compact`).
   210바이트가 남았는데도 9바이트를 못 넣는 일이 실제로 있었다.
3. 그래도 안 되면 PE 에 데이터 섹션을 붙인다(`pesection.py`). 파일이 커지므로
   **ISO 여유가 있어야 하고**, 없으면 시도하지 않는다.
4. 끝내 안 되는 것은 **원문을 유지**한다.

포인터를 찾을 때 두 가지를 조심해야 한다:

- **패치한 뒤에 찾으면 안 된다.** 새로 쓴 바이트가 우연히 VA 와 같아져 없던
  참조가 생긴 것처럼 보인다(`平岸駅` 이 1곳 → 3곳으로 늘었다). 손대기 전
  원본에서 찾는다.
- **`.reloc` 로 검증한다.** 모듈이 다른 베이스로 올라갈 수 있으므로 진짜
  포인터는 반드시 재배치 테이블에 등록돼 있다. 우연한 바이트 일치를 거른다.

**실패한 결과는 절대 쓰면 안 된다.** `apply` 는 옮길 문자열의 옛 자리를 먼저
비우므로, 넣을 곳을 못 찾으면 그 자리에 이미 다른 문자열이 들어가 있고 포인터는
옛 자리를 가리킨 채 남는다. 화면에 엉뚱한 문장이 나온다(TRFNAMEIN 에서 겪었다).

## 3. **번역하면 안 되는 문자열** — 가장 중요

### 3.1 조회 키 (EDL 심볼 이름)

엔진은 EDL 가상머신의 전역변수를 **이름으로** 찾는다.

```
CTRFCmdMenu::Start (KITACMDMENU 0x10002560)
  → IGelFlexible::GetVarByName("移動表示", &moveMask)   (KITAHEGEL 0x10004908)
     → ISymbol 이 north01.sym 해시표에서 조회
       (SYMBOL 0x10001100 해시, 0x10001170 버킷 순회, 마지막에 strcmp)
```

`north01.sym`(PLOT.CB 안, 그룹 4개 89/139/396/2 = 623개)의 그룹1 101번이
`移動表示`, 102번 `メニュー表示`, 103번 `セーブ場所`다.

이 이름을 DLL 에서 한글로 바꾸면 해시가 빗나가고 strcmp 가 실패하는데,
**실패해도 조용히 1을 돌려주고 출력 인자를 안 건드린다.** 마스크가 초기값 0으로
남고, 0이면 이동 목록 대신 3D 시내 지도가 열린다 — ８월１일 밤에 목욕이 안 뜨던
증상이 이것이었다. 죽지 않고 조용히 틀리므로 찾기가 어렵다.

방 이름(`風呂`, `書斎` …)은 비트별 **표시 라벨**일 뿐이라 번역해도 된다.

### 3.2 대사 마크업의 키 / 값

`KITAE.DLL` 의 `主人公名前`, `名前`, `マフラー` 는 대사의 `&主人公&` 치환에 쓰이는
키다. `デビル`·`ＮＡＲＫ`, 색 이름(`赤い`, `青い` …)도 같은 계열.

### 3.3 리소스 파일명·클래스명·서식 틀

`menu/phs1000.3dp`, `KitaEvent`, `EDL`, `@００００００００`.

## 4. 키인지 표시인지 가르는 법

**유일하게 믿을 수 있는 건 코드가 그 주소를 만지는가다.** `north01.sym` 에 이름이
있다는 것만으로는 부족하다 — 우연히 단어만 겹치는 것이 많다(`五稜郭`, `元町`,
`ベイエリア`, `四稜郭`). 이름만 보고 막았더니 93개가 걸려 지명까지 일본어로
돌아갔다.

`kitae/build/xref.py` 의 판정:

| 판정 | 근거 |
|---|---|
| **키** | `.text` 리터럴 풀에 VA 가 있다 → 레지스터에 실려 조회 함수로 간다 |
| **키** | `.rdata`/`.data` 에서 VA 바로 뒤 4바이트가 작은 정수 → `{이름, 비트}` 표 |
| **표시** | 라벨 배열·구조체의 이름 칸에만 있다 |

확신이 안 서면 키로 본다. 그리고 **한 모듈에서라도 키면 모든 모듈에서 키로**
묶는다 — 같은 이름이 모듈마다 다르게 판정되는데(`ＵＦＯできる` 가 COMMONSAVE 에선
키, TRFOPTIONGAME 에선 표시) 표 형태를 다 알아보지는 못한다. 근거는 비대칭이다:
잘못 번역하면 증상이 조용하고, 못 번역하면 눈에 띈다.

지금 74개가 막힌다. 빌드가 자동으로 판정하므로 손으로 목록을 관리하지 않는다.

기록은 `data/` 에 남는다:

| 파일 | 내용 |
|---|---|
| `data/symbols.json` | `north01.sym` 의 심볼 이름 623개, 그룹별. **이름 순서가 곧 EB 가 쓰는 번호**라 순서를 바꾸면 안 된다 |
| `data/untranslatable.json` | 이번 빌드에서 키라서 건너뛴 문자열 (모듈·오프셋·원문) |

그룹 구성: 0=화자 89, 1=이벤트 139, 2=플래그·변수 396, 3=기타 2.
`移動表示` 는 그룹1 의 101번이다.

## 5. 아직 못 하는 것 — 키이면서 표시인 문자열

`ITEMMENU` 의 아이템 표는 `{u32 id, char* 심볼이름, char* 표시이름, char* 설명,
u32 아이콘}`(20바이트) 인데 **원본이 심볼이름과 표시이름에 같은 문자열을
가리킨다.** 그래서 지금은 안전하게 막아 아이템 이름 9개가 일본어다.

포인터를 갈라 표시이름만 새 한글 문자열을 가리키게 하면 풀린다.

## 6. 글자 폭과 정렬

- **UI 원문은 전부 전각**이라 모든 글자가 짝수 바이트 위치에 온다. 반각을 끼우면
  그 뒤가 홀수로 밀리고, 엔진이 고정 위치에 써 넣는 자리(포트 문자 `Ａ`, 소켓
  번호 `１`)에서 한글 한 글자의 가운데를 덮어써 깨진다. 낱말 사이 공백도 전각.
- **앞뒤 정렬용 반각 공백은 보존한다.** 타이틀 메뉴는 앞의 반각 공백 수가
  `7 − 전각 글자 수` 로 떨어진다(중심이 반각 7칸). 미니게임 목록은 앞뒤 공백으로
  폭을 맞춰 두었으므로 원문과 같은 폭을 유지해야 한다.
- 엔진이 값을 써 넣는 자리(`Ａ`, `１`)는 **원문과 같은 글자 위치**여야 한다.

## 7. 씬 제목(INIS.CB)은 손댈 필요 없다

`RESOURCE/SCN/*.INI` 의 `○８月１日／夜／ローズヒル南平岸／春野家／風呂` 같은 제목은
**제작진 문서**다. 어떤 코드도 이 장소 필드를 대조하지 않는다 — 여는 곳은
TRFSCENELAUNCH 의 디버그 씬 선택기뿐이다. 번역해도 무해하지만 아무 효과가 없다
(`kitae/build/scenes.py` 는 꺼 두었다).

## 8. 빌드는 늘 원본에서

`work/build` 를 매번 비우고, 입력은 전부 **원본 디스크에서 꺼낸 `work/orig`
캐시**를 쓴다. 이전 산출물에서 시작하면 지난 패치가 얹힌 채로 쌓인다 — 폰트에서
한 번(`Font()` 기본 경로가 빌드 산출물을 가리켰다), UI 재배치에서 한 번 겪었다.

## 9. 검증

디스크에서 되읽어 확인한다. 빌드 중간물을 보면 안 된다.

- 모듈 크기가 그대로인가 (PE 섹션을 붙인 경우는 예외)
- **포인터를 따라간 내용**이 번역문과 같은가
- 우리 소유(문자열 자리 + 포인터 슬롯) 밖이 바뀌지 않았는가
- 심볼 이름이 원문 그대로 남아 있는가

## 저장 슬롯 머리글 순서 — 날짜·시간대를 앞으로 (2026-09-18, `save_header_reorder`)

저장/불러오기 화면의 슬롯 머리글은 TRFVMSVIEW.DLL `0x10002cf4` 가 조각을 **코드로 조립**한다:
`[도시 8B][스폿 …30B 고정 필드][월 2자][月][일 2자][日][시간대]` + `\n　　保存日時　YYYY/MM/DD hh:mm`.
장소는 서브루틴 `0x10002f38` 이 버퍼 앞에 고정 배치(15개 전각공백 strcpy 뒤 도시를 +0, 스폿을
+8 에 memcpy)하고, 월·일은 한 자리면 전각공백으로 채운다. 시간대는 표 `0x100124ec`(`　朝`·`午前`
·`午後`·`夕方`·`　夜`, 5 이상은 `不正`).

한국어에서는 `12월 30일 밤 / 삿포로 로즈힐 미나미히라기시` 순이 읽기 좋아 순서를 바꿨다.
문자열만으로는 안 되므로(날짜는 동적) **코드 패치**(`data/dllpatch.json`, `option:
"save_header_reorder"`, 생성기 `tools/gen_savehdr_patch.py`):

  * `0x10002d06` bsr(장소)·`0x10002d0c` jsr(strlen)·`0x10002d1c` add r0,r9 → nop: 날짜가 버퍼 앞에.
  * HOOK D `0x10002d66`(12B): `月` 뒤에 전각공백 하나(`１２월　３０일`).
  * HOOK C `0x10002e22`(12B): 시간대의 끝(NUL 탐색) 뒤에 반각 공백(12px) → 장소 서브루틴(r5=@(16,r8),
    r6=r9) → r9+=30 → 개행 → r5=`保存日時`, r0=strcpy 를 원본 리터럴 풀(`0x10002fc0/c8`)에서 읽어 복귀.
    ★ `hook_code` 는 거리를 r0 에 만들어 `bsrf r0` 하므로 **스텁 진입 시 r0 은 원본 값이 아니다.**
    처음 판은 `add r0,r9`(strlen 결과라 믿고)로 시작해 r9 가 4,970B 뒤로 갔고 화면엔 날짜만 남았다
    (2026-09-19, SH4 미니 에뮬레이터로 재현·수정).
  * 스텁 C(64B)+D(40B)는 `.text` 꼬리 케이브 `0x10004198`(104B)를 꽉 채운다. **절대주소 없음** — `bsr L;
    sts pr,rN` 으로 얻은 PC 에 거리 상수를 더해 풀·함수에 닿는다(재배치 불필요). `.text`
    VirtualSize 를 100B 키운다.
  * 시간대 문자열은 앞에 전각공백(`　아침`·`　오전`·`　오후`·`　저녁`·`　밤`·`　오류`, avail 7).

결과(2026-09-19 형식): `12월 30일`+EM+`밤`+EM+`삿포로`+EM+`로즈힐　미나미히라기시` — 숫자는 ASCII 셀(15px),
월-일 사이 어절 공백(9px), 한 자리 월·일 앞자리는 FIGURE SPACE(U+2007, 15px), 날짜-시간대·시간대-장소·
도시 필드 채움은 EM SPACE(24px).
버퍼는 슬롯당 88B(호출자 `0x10002140`, 92B 레코드 +4), 새 줄은 84B. **스폿명은 11자(22B) 이하**
— 도시 8B 와 합쳐 30B 필드를 넘으면 뒤가 잘린다(`ＪＲ札幌駅南口` 를 `ＪＲ삿포로역　남쪽　출구`
11자로 맞춘 이유). 끄기: `kitae config set save_header_reorder false`.

## 보호 항목(`fixed`)과 raw 인코딩 (2026-09-18, KO-TEXT-RULES)

한국어 문자 규칙(docs/KO-TEXT-RULES.md)으로 `ko` 의 ASCII·공백·합자는 2바이트 셀로 재할당된다.
그러나 엔진이 **바이트로 조립·해석·정렬**하는 UI 문자열에 그걸 적용하면 깨진다. 그래서
`uipatch.is_fixed(e)` 가 참인 항목은 옛 인코딩(`hangul.encode(raw=True)`: ASCII 1바이트, U+3000 →
0x8140, 합자 없음)으로 넣고, 변환기·검사기도 건너뛴다.

판정(셋 중 하나): 항목에 `"fixed": true` / 원문(ja)에서 마크업(`&マフラー&` 등)을 뺀 나머지에 ASCII·탭이 있음(서식 템플릿 `@００００００００`,
색인 접두 `0ローズヒル`, `	札幌駅南口`, 반각 정렬 공백 `   最初から`) / 원문이 전각 공백으로 시작·끝남
(조각 조립 `　朝`·`　　保存日時　`, 15칸 공백 필드). 사람이 `fixed` 를 단 곳: KITATITLE 67976,
TRFOPTIONGAME 89984·90008(반각 공백으로 칸 맞춘 라벨). 보호 항목의 `ko` 는 예전 관례(U+3000·
반각 공백)를 그대로 쓴다 — 예: 저장 슬롯 스폿명 `0ＪＲ삿포로역 남쪽 출구`(30B 필드에 22B). 보호 항목의
U+3000 은 0x8140 이고 폭표에서 EN 과 같은 12 다 — 24 의 절반이라 반각 단위로 가운데 정렬이
맞는다(사용자 지시, 9 는 정렬이 안 맞음). EM SPACE 24 는 전용 셀.
