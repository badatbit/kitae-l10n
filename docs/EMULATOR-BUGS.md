# 에뮬레이터 버그와 우회 패치

이 게임은 **Windows CE 타이틀**이다. 디스크 부트스트랩이 그렇게 말한다.

```
부트 파일    0WINCEOS.BIN
주변기기     0x00199801   ← 최하위 비트 = WinCE
대응 지역    J
```

WinCE 게임은 SH4 의 MMU 를 실제로 쓴다. 대부분의 드림캐스트 게임은 안 쓰기 때문에
에뮬레이터들이 오래도록 MMU 를 대충 넘겼고, 그래서 WinCE 타이틀은 지금도 가장
까다로운 부류다. **여기 적는 것은 게임의 버그가 아니라 에뮬레이터가 못 하는 일이고,
우리가 디스크 쪽에서 피해 가는 방법이다.**

## ★ 규칙 — 원본에서 재현되는지 먼저 확인한다

번역 때문에 생긴 문제와 에뮬레이터 문제는 증상이 똑같이 보인다. 아래 [선택지
게이트](#선택지-게이트--선택-상자가-안-그려진다) 를 쫓을 때 창 테이블·EB·타이밍·음성
표를 다 뒤지고 나서야 원본에서도 같다는 걸 알았다. **순서를 뒤집지 말 것.**

1. **패치하지 않은 원본 디스크**에서 같은 자리를 확인한다
2. **다른 에뮬레이터**에서도 확인한다 (redream ↔ Flycast)
3. 둘 다 재현되면 여기 적고, 우회 패치는 `emulator_fixes` 아래에 둔다

우회 패치는 번역과 섞지 않는다. 켜고 끌 수 있어야 하고, 끄면 원본과 같은 바이트가
나가야 한다.

## 선택지 게이트 — 선택 상자가 안 그려진다

**증상.** 선택지가 나와야 할 자리에서 대사만 떠 있다가, ２~３초 뒤 아무것도 고르지
않았는데 고른 것처럼 진행된다. 상자가 화면에 없으니 고를 수가 없다.

**확인 (2026-08-08).** redream v1.5.0-1231 · Flycast 2.6 **둘 다**, 그리고 **패치하지
않은 원본 디스크에서도** 재현된다. 번역과 무관하다.

### 무엇이 갈랐나

선택지를 여는 `0x73`/`0x74` 앞에 두 갈래가 있다.

| 앞선 옵코드 | 곳 | 결과 |
|---|---|---|
| `0x2E` · `0x46` | 524 | 뜬다 |
| `0x6E`\|`0x6F` · `0x24` · `0x42` · `0x2E` · `0x46` | 508 | **안 뜬다** |

`0x6E`/`0x6F` 는 `<u16 A> <u16 B>` 두 워드를 받는다.

| | 값 | 해석 |
|---|---|---|
| `A` | ９０·１２０·１８０·２４０·２６０ 다섯 가지뿐 (１２０ 이 ６５%, ３３０곳) | **거의 확실히 타임아웃.** ６０fps 로 １．５~４．３초이고, 가장 흔한 １２０ = ２초가 관찰된 멈춤 시간과 맞는다 |
| `B` | ３３~１４７, 서로 다른 값 ５１개 | **모른다** — 아래 참고 |

**타이머 자체는 정상으로 돈다.** 멈췄다가 기본값으로 넘어가므로 시간은 흐르고
있다. 안 되는 것은 그리기뿐이다.

#### ★ 미해결 — `B` 가 무엇인지 모른다

세 가지를 재 봤고 전부 아니었다.

```
창 번호와 같은가      508곳 중   2곳
화자와 상관있는가     없음 (琴梨·鮎·由子 모두 33~43 에 몰린다)
앞 창 글자 수인가     508곳 중   9곳
```

그래서 **"제한 시간이 있는 선택지가 안 그려진 것" 이라고 단정할 수 없다.**
남은 가설이 둘이고, 둘 다 지금까지의 관찰과 모순되지 않는다.

  * **(가) 시간 제한 선택지.** `A` 가 제한 시간, `B` 는 게이지·시계 같은 UI 부품
    번호. 그 부품이 안 그려지면서 상자까지 같이 빠진다.
  * **(나) 다른 층에 그리는 선택지.** `0x6E` 가 표시 방식을 바꾸고(연출 컷 위에
    겹쳐 그리기 등) `B` 가 그 층·컷 번호. 시간 제한은 그 방식에 딸린 부수 효과.

우회는 어느 쪽이든 유효하다 — 게이트를 지우면 평범한 선택지가 되기 때문이다.
다만 **원작이 그 자리에서 어떤 연출이었는지는 아직 모른다.** 갈라 보려면:

  1. `0x78`/`0x79` 가 쓰는 VSC 컷 번호와 `B` 의 범위가 겹치는지
  2. `0x85`/`0x87`/`0x89` 가 등록하는 KitaEvent 트랩 ２０바이트 레코드에 `B` 가
     나오는지
  3. `TRF/KITAHEGEL.DLL` 을 역어셈블해 `0x6E` 핸들러가 `B` 를 어디에 쓰는지
     (capstone 이 있으면 된다)

３번이 확실하지만 품이 든다.

#### ★ 해결 — `0x6E` 핸들러 역어셈블 (2026-08-17, `TRF/KITAHEGEL.DLL`)

VM 은 `KitaheGel.dll`. 디스패치 테이블 `0x100131B4`(핸들러=`*(base+op*4)`), 오퍼랜드
길이표 `0x10013428`, 메인 루프 `0x10005F34`. 핸들러 주소:

| op | 이름 | 핸들러 |
|---|---|---|
| 0x6B | message | 10003764 |
| 0x6D | message.sel | 100038c4 |
| **0x6E** | **message.sel2** | **10003944** |
| 0x6F | message.sel3 | 100039c4 |
| 0x73 | menu.item | 10003b28 |
| 0x74 | menu.item2 | 10003b80 |

`0x6E` 핸들러(`10003944`)가 하는 일:
- `A`(첫 워드) → 메시지 객체 `gel@40 -> vt[36](A+15, mode=5)`. **평범한 메시지 `0x6B`
  는 같은 객체에 `vt[36](25, mode=0)` 를 부른다.** 즉 `A` 는 이 표시 메서드의 **첫 인자
  (프레임 수)**로 들어가고 모드만 5(선택형)로 바뀐다 → **`A` 는 표시/입력 타이머가 확실**.
- `B`(둘째 워드) → 선택 관리자 `gel@24` 의 `+0x300` **32바이트 레코드 테이블**[count]에
  기록(record.field). 뒤이어 `gel@24 -> vt[84]`(커밋), `gel@24+0x350` 플래그를 0 리셋.
- `gel@24` 는 선택/메뉴 관리자다: `+0x300` 트랩 레코드 테이블, `+0x348` 메뉴 슬롯 배열
  포인터(`0x74` 가 씀), `+0x350` 매 op 후 리셋 플래그. `+0x300` 테이블은 `message.sel`
  계열(`0x6D~0x70`)만 채우고 관리자 자체 업데이트 로직(`0x10002034`·`0x100021bc` 등)이 읽는다.

**결론 — 가설 (나)(다른 층에 그리기) 는 배제된다.** `0x6E` 는 평범한 메시지와 **같은
객체**(`gel@40`)로 표시하고 층/컷을 바꾸지 않는다. 실제는 **(가)에 가깝다: 시간 제한
선택.** `A` = 타임아웃 프레임, `B` = 실행 컨텍스트 레코드 테이블에 실리는 선택별 파라미터.
에뮬 증상 = 이 선택형 표시 모드(`vt[36]` mode 5)의 상자가 에뮬에서 안 그려지는데
타이머(`A`)는 정상으로 흘러 → 타임아웃 → 기본값 진행.

#### `B` 배관 추적 (2026-08-17) — 소비자는 `vt[52]`

`gel@24` 는 별도 "선택 관리자"가 아니라 **스크립트 실행 컨텍스트 객체**다(세터 `0x10003258`:
`gel@24 = ctx`, `gel@28 = ctx+20`; 커서 pc/operand 가 `ctx+20`). 그 안에:
- `+0x294` 상태/커서 워드, `+0x300` count, `+0x304` **32바이트 레코드 배열**(stride 32).
- 한 메시지 창이 레코드 한 칸을 쓴다. `0x6E` 는 그 칸의 `+4`(u16)에 `B` 를 넣고(평범한
  `0x6B` 은 `B` 를 안 쓴다), `vt[84]` 로 커밋한다.
- 소비자 `0x10002034`: 레코드의 `B`(record+4)를 읽어 **`ctx->vt[52](B)`** 를 호출.

**`B` 의 정확한 의미 = `vt[52]` 본문인데 정적 분해가 막혔다.** `ctx` 는 다중상속 COM류
객체(RTTI `ITRFInterface`)라 vtable 이 필러(`0x100069d4`)로 뭉쳐 있고, 인스턴스는
다른 DLL 에서 생성돼 primary vtable base 를 정적으로 특정 못 한다. → 남은 확실한 길:
(a) 289 장면에서 `ctx+0x304` 32바이트 레코드를 **라이브로 덤프**해 `B`(=46) 이웃 필드로
역할 추정, 또는 (b) `vt[52]` base 를 더 파기.

**경험적으로 배제한 `B` 가설 (508 게이트 전수):**

| 가설 | 결과 |
|---|---|
| 창 번호 | 무관 (2/508 우연 일치) |
| 화자 | 무관 (화자별로 33~147 넓게 퍼짐) |
| 타임아웃 `A` 와 상관 | 무관 (corr **−0.04**, 독립) |
| 선택지(뒤 메뉴) 글자수 | 무관 (totch=18 → B=33/36/42) |
| 게이트된 메시지 글자수 | 무관 (corr **0.05**; B=34↔58자, B=63↔9자) |

`B` 는 **floor=33, 34~36 피크, 147 까지 감소 꼬리**(길이형 분포지만 어떤 내용 지표와도
무상관). 값 33(=0x21) 바닥 + 내용 무상관 → 예약 슬롯 뒤의 **id/인덱스(트랩·라벨·
UI부품)**로 추정되나 미확정. 289 실측: `0x6B`(289) → `0x6E A=180 B=46`(화자2=琴梨) →
`0x73`(290, 선택지 3줄). 전체 디스어셈 덤프 `tmp/gel_full.txt`.

#### 정밀 증상 + 모드 스왑 실패 (2026-08-17)

라이브 재확인: **대기 아이콘은 뜨고 입력도 먹는다(누르면 아이콘 사라짐). 그 다음
"선택지 팝업 그리기"만 실패**한다. 즉 타이머·입력·로직은 정상이고 순수 렌더 실패다.

`vt[36]` 표시 모드 비트가 원인이라는 가설을 검증했다 — 안 쓰이는 형제 옵코드로 스왑
(`0x6E`(mode 5)→`0x70`(mode 13), `0x6F`(mode 1)→`0x6D`(mode 9); B·A·오퍼랜드 길이 4
동일, mode 에 bit3 만 추가). 508 곳 스왑해 인게임 확인: **팝업 여전히 안 뜸.** →
**모드 비트는 원인이 아니다.** 렌더 실패는 `message.sel` 계열(어느 모드든)이 만드는
타임드-선택 상태 자체에 있다(구체 소비자 `vt[52]`/팝업 렌더러가 크로스-DLL 이라 정적
분해 불가, VA 라 라이브 read 불가). 우회는 `ungate`(NOP) 유지가 확실하다.

게이트는 음성과 강하게 붙어 다닌다.

```
0x6E/0x6F 있음 · 앞 창 유성   495곳
0x6E/0x6F 있음 · 앞 창 무성    13곳
0x6E/0x6F 없음 · 앞 창 무성   300곳
0x6E/0x6F 없음 · 앞 창 유성    50곳
```

９７% 가 유성 창 뒤다. 다만 **음성이 기준은 아니다** — `KOTORI_01` 창４５ 는 앞 창이
무성인데도 게이트가 걸려 있고 증상이 난다. 기준은 게이트 옵코드 자체다.

`0x2E` 의 오퍼랜드(４ 대 ８)는 원인이 아니다. `0x2E 4` 는 ６１３곳이 쓰는 가장 흔한
값이고 그중 다수가 멀쩡히 뜬다.

### 우회

`0x6E`/`0x6F` 다섯 바이트를 `0x00` 으로 덮는다 →
[`kitae/build/ebgate.py`](../kitae/build/ebgate.py)

```
전  0x6E b4 00 2e 00 · 0x24 · 0x42 · 0x2E · 0x46 · 0x73
후  0x00 ×5          · 0x24 · 0x42 · 0x2E · 0x46 · 0x73
```

안전한 근거 셋:

- `0x00` 은 전 대본에 **２１,００３곳** 나오는 문장 구분자다(`0x6B` 뒤에만 ６,９７６곳).
  다섯 바이트를 덮으면 빈 문장 다섯 개가 된다.
- 게이트만 빠진 이 형태가 **원본에 이미 ９곳** 있다(`KAORU` 창９, `KOZUE` 창２７９ 등).
  엔진이 처리하는 형태다.
- 길이가 그대로라 점프 목적지도 `tail_off` 도 움직이지 않는다.

**결과 (2026-08-08 인게임 확인).** 선택지가 뜬다. ５０８곳 전부에 적용된다.

### 잃는 것

`A` 가 타임아웃이라면 시간 제한이 사라진다 — 원래 ２~３초 안에 못 고르면 기본값으로
넘어갔는데 이제는 고를 때까지 기다린다. **"뜸을 들이는 것 자체가 선택"인 장면이
있다면 거기서 멈춘다.** 그런 자리를 만나면 그 창만 게이트를 남기도록 예외를 두면
된다.

`B` 가 연출 층·컷을 가리키는 것이었다면 **그 연출도 함께 사라진다.** 무엇을
잃었는지는 `B` 를 밝혀야 알 수 있다.

지금은 상자가 안 그려져 **항상** 기본값으로 넘어가는 상태이므로, 고를 수 있게 되는
쪽이 낫다고 보고 켜 둔다.

### 끄기

```json
"emulator_fixes": { "choice_gate": false }
```

끄면 EB 는 원본 바이트 그대로 나간다.

## 미해결

### 가라오케에 들어가면 리셋된다

**증상.** 가라오케 화면에 들어가는 순간 리셋된다.

**상태.** 원인 미상. 우리가 그 화면에서 바꾼 것은 `TRFKARAOKE.DLL` 의 조작 설명 두
줄뿐이었고(여유 ８ B 로 빠듯하게 제자리에 들어갔다), 지금은 **되돌려 원본 그대로**
나간다. 가사(`歌詞.SMF`·`歌詞.EB`)는 애초에 손댄 적이 없다 — 디스크 대조로 확인했다.

되돌린 뒤에도 리셋되는지 아직 확인 못 했다. 그래도 리셋된다면 다음을 의심한다.

- 폰트(`TRFSTRINGS.DLL`). 가사가 쓰는 글리프 칸을 우리가 한글로 덮었을 수 있다.
  `used_cells` 의 예약 목록은 **대사**를 훑어 만든 것이라 가사 쪽은 안 세었다.
- WinCE 특유의 화면 전환. 이쪽이면 위 규칙대로 원본에서 먼저 재현해 봐야 한다.

되살릴 오프셋은 [`tools/legacy-src/minigames.py.txt`](../tools/legacy-src/minigames.py.txt) 의
`TRFKARAOKE` 블록에 주석으로 남겨 두었다.

## 에뮬레이터 설정

디스크는 `대응 지역 J` 인데 두 에뮬레이터 다 USA·English 로 잡혀 있었고, 실기 BIOS
없이 HLE BIOS 로 돌고 있었다. WinCE 타이틀은 부팅 과정에서 BIOS 를 더 깊이 쓰므로
일반 게임보다 잘 어긋난다. 원인 모를 증상을 쫓기 전에 아래를 먼저 맞춰 둘 것.

| | 맞춰야 할 값 |
|---|---|
| 지역 | Japan |
| 언어 | Japanese |
| BIOS | 실기 `dc_boot.bin` (HLE 아님) |
| Flycast `aica.DSPEnabled` | `yes` |
| redream `frameskip` | 끔 |
